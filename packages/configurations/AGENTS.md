# packages/configurations

The shapes of a review artifact and the instructions an agent writes it with. Read [prompt configurations](../../docs/vocabulary/prompt-configurations.md) and [review artifact](../../docs/vocabulary/review-artifact.md) before changing anything here.

## Rules

- **Shapes and data only.** The package holds the artifact's types and schema (`src/artifact/`), the band schemas the review page renders (`src/bands/`), the field catalog and Markdown. It holds no function that builds, filters or decides anything, apart from the walk that reads the catalog out of the schema: building a band belongs to `packages/codegraph`, and reading files and resolving a field for a configuration belong to `apps/backend`.
- **One entry.** `src/index.ts` is the only module another project imports, as `@flightplan/configurations`. It depends on no other project of the workspace.
- **Every type of the artifact is written by hand beside its schema.** `src/artifact/artifact-schema.ts` holds the zod schema a stored artifact is parsed with, and `src/artifact/review-artifact.ts` the types, and the two must agree: change both in the same change. The Journey Flow Diagram is `JourneyFlowDiagram`, `JourneyNode`, `TriggerLabel` and `JourneyNodeEdge`, parsed by `journeyFlowDiagramSchema`. Its nodes are checked, and what they refer to is not: a `CodeBlock`, the `astCodeGroup` and the `importGraphGroup` are `z.custom`, so a parse hands back the same objects and every alias of the diagram holds.
- **The shapes of the code graph are here too.** `src/code-graph/code-blocks.ts` holds a code block, a file and a group as they are in memory, with `CODE_BLOCK_TYPES`, and `src/code-graph/import-graph.ts` a file of the import graph. `packages/codegraph` fills them and re-exports the types, and a journey node's `type` is a `CodeBlockType`.
- **A blast holds two graphs.** `nodes` and `edges` are the export bound: the files that use the change, with the `impactType` and `impactReason` an agent or an author writes. `importBound` is optional, so that an artifact stored before it existed still parses, and holds the files the change uses as nodes of `path` and `diffType` alone, with edges of the same shape. The Blast Diagram band carries them as `views`, with `defaultViewId` and the `assessmentForm` of the author's impact form.
- **A band schema is what the frontend receives.** `src/bands/band-schemas.ts` holds the display-ready shapes of the Journey Flow Diagram, the Blast Diagram and the Code Walkthrough, and the prose, code line and code link shapes they share. A node of the journey band holds the nodes inside it and has no position: `packages/ui` places it. A field is added there together with the builder in `packages/codegraph` that fills it.
- **A field's configuration is registered on its schema.** `src/artifact/field-configuration.ts` holds the `configurations` registry and the `FieldConfiguration` shape. Every field an agent can ask about carries its configuration inline in `src/artifact/artifact-schema.ts`, as `.register(configurations, { … })` on the field's own Zod schema: its `version`, its `configurationType`, the `fieldDescription` file, an `exampleValue`, and for an enum the `values` file of each option. An editable field also carries the `_ui` the settings screen renders it with and its `defaultInstruction` file. A static field carries the `summary` line the agent's index shows. Never keep a field's configuration in a list beside the schema.
- **The catalog is read from the registry.** `src/artifact/field-catalog.ts` walks `reviewArtifactSchema` and lists every registered configuration as `FIELD_CONFIGURATIONS`, after the three that belong to no field: `writingStyle`, `codeLinks` and `artifactFormat`. `INSTRUCTION_FIELDS` in `src/index.ts` is that list with each field's public path, which is its `fieldDescription` without the extension.
- **One file per catalog entry, named after the field's path.** `src/system-instructions/<field>.md` says what a field is and is the same for every configuration. `src/default-configurations/<preset>/<field>.md` says how that preset writes an editable field, and `<field>.<option>.md` says what one option of it means.
- **A field is added in three places at once**: its registration on the schema, its system instruction, and its Standard instruction when it is editable. The test fails on a catalog entry with no file and on a file with no entry.
- **A section switch is data, and an artifact holds its own.** `SECTION_NAMES` in `src/artifact/kinds.ts` names the optional sections: `journey`, `blast`, `walkthrough` and `findings`. `PRESET_SECTIONS` in `src/index.ts` switches each on or off for every preset, `SECTION_FIELD_PATHS` gives the path every field of a section starts with, and `SECTION_LABELS` its name in prose. A review artifact carries its switches as `sections`, optional so that an artifact stored before it existed still parses. Code that reads a switch reads it from the artifact, never from the name of a preset.
- **Standard is complete.** Every editable field and every option has a file in `standard/`. Another preset's folder holds only what it writes differently, and the rest is read from `standard/`.
- **An instruction describes the artifact as it is stored and the tools as they are.** A field name, a tool name or a refusal named in an instruction must exist in `src/artifact/` or in `apps/backend`. Change both in the same change.
- **A path is public.** The review skill and agents ask for fields by path, so renaming one is a breaking change: update `plugin/skills/review/SKILL.md` with it.
