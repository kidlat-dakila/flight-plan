# packages/ui

Flight Plan's component library: shadcn primitives and the shared presentational components that pages compose, such as CodeLink, CodeBlock, Journey Flow Diagram and Blast Diagram. Read [architecture](../../docs/agents/architecture.md) and [react](../../docs/agents/react.md) before changing anything here.

## Rules

- **Props in, JSX out.** Components receive all data and callbacks through props. They never call an API, use tRPC or TanStack Query, read the router, or touch browser storage for domain data.
- **Code is drawn through Code Hike.** `CodeBlock` hands the lines the backend highlighted to `Pre` of `codehike/code` as tokens and annotations, and draws the row, the mark and the definition with annotation handlers. The definitions arrive as its `definitions` prop, and a definition's written description is drawn by its `renderDefinitionDescription` prop, which `FileSection` and `NodeCodeView` fill with `HoverProse`, so `CodeBlock` does not import `Prose`. It never calls Code Hike's `highlight`.
- **The Journey Flow Diagram is drawn through React Flow.** `lib/journey-layout.ts` decides where every node, row and line goes: a line that closes a loop moves no node, and is led below the nodes it passes (`withoutLoops`, `pointsBelow`), and `lib/journey-flow.ts` turns that layout into what `@xyflow/react` draws: a node for each plate, with a node inside another as its child, a handle at each end of a line, and an edge for each line that bends where the layout bends it. A line joined to a row is three edges: the line between the two nodes, drawn under the nodes, and the short line to each row, drawn above them. React Flow never arranges anything, and for a reviewer nothing on the diagram can be dragged, connected or selected. An author gets the `authoring` prop: a card at the top level is dragged, a dot at the right of each row starts a line and a dot at the left, the top and the bottom of each card ends one, as does a drop anywhere on a card, which ends the line at the nearest of those sides (`nearestSideOf`), and a drop on the empty board leaves a plus at the end of the line, a node of its own type that is kept in the component and never saved, whose press asks for a card there (`onAddCardAtLineEnd`), a pressed line is selected and removed from the toolbar, the toolbar of the board adds a card, clears the diagram and removes it (`onAddCard`, `onClearDiagram`, `onRemoveDiagram`), and every card has a button to modify it and one to delete it. The component draws and reports, and the page saves. `lib/journey-arrangement.ts` puts the cards with a stored position where it says, stacks the others beside them, and ends a line at the side it reaches. The dots are listed in the `handles` of each node as well as drawn, because React Flow reads the ends of a connection from that list. `DiagramBoard` keeps the zoom and the pan and hands them to `renderCanvas`, where they are the viewport of React Flow. Its zoom, reset view and full screen are not on the board: it hands them to the Review Navigator through `navigation`, after the `leadingGroup` its diagram hands it (collapse all for the Journey Flow Diagram, the views for the Blast Diagram), and in full screen it draws `ReviewNavigatorBar` inside its dialog. The author's actions are the board's own toolbar, sticky below the band while the board is inline and fixed below the top of the board in full screen, and every `IconButton` on it takes `labelPlace="beside"`, which shows the label beside the icon and leaves out the `Tooltip` of `blocks/tooltip.tsx` that an `IconButton` shows its label in elsewhere, with no `title` of the browser. Its stylesheet is imported in `src/styles/globals.css` into the `components` layer, so a Tailwind class overrides it. Tests run with the `ResizeObserver` of `src/lib/__tests__/jsdom-setup.ts`, which React Flow needs and jsdom lacks.
- **The Blast Diagram switches between the views the backend sent.** `BlastBand` takes `views` and `defaultViewId`, holds which view was chosen, and draws that view's counts, key and board. With more than one view it hands a button per view to the Review Navigator, through the `navigation` of `BlastDiagram`: E for the export bound and Q for the import bound, pressed for the view that shows and with the view's `description` as its title. The diagram keeps its zoom and its full screen across a switch, and a selected file that the other view lacks closes the side panel.
- **The Blast Diagram is read-only but for the impact of a file.** `BlastBand` takes `renderImpactEditor`, `null` for a reviewer. For an author the side panel of a file that has an `assessment` shows the form's `editLabel` as a link button, and pressing it draws what `renderImpactEditor` returns in place of the impact reason and the fixed sentence, until the editor calls `onClose`. The component holds which file is being edited and nothing of the form.
- **A form that more than one page draws takes its actions as `children`.** `AgentsForm`, `ForgesForm` and `DefaultConfigurationForm` hold the fields and what the user chose, call `onSubmit` with the choice, and render their `children` at the foot of the `<form>`, where the page puts its submit button. They show a `FormProblem` (`lib/form-problem.ts`) under the field it names; the page shows one that names no field.
- **A section that was not generated is drawn by `GenerationOffer`.** It takes the offer the backend worded (`anchorId`, `heading`, `message`, the two labels of its button), whether the request runs, and why it failed. Its `kind` picks the frame: `board` is a band of its own with the offer over an empty diagram board, and `notice` is the offer under a smaller heading, for a part inside another band.
- **The Review Navigator shows the controls of the section on screen.** `ReviewNavigator` wraps a review page, takes its `rail`, and works out which rail section is most present on screen: the larger of its share of the window and the share of itself in view. A section registers its controls under its anchor with `useNavigatorSection(anchorId, groups)`, built from `navigatorButtonOf`, a `menu` of checkbox choices and submenus of them, or a `position`, and `ReviewNavigatorBar` draws Jump to, then Back (A) and Next (D) to the rail sections around the one on screen (`sectionStepsOf`), then those groups. A section that registers a control for A or D takes that key from Back or Next (`withSectionSteps`); `CodeWalkthrough` does so, and puts the step `useSectionSteps` gives it in place of its waypoint step at the ends of its segment. `ContextBand` registers through `useAccordionNavigation`, which also holds which accordion sections of `Prose` are open through `AccordionOpeningContext`; `DiagramBoard` registers the view controls; `CodeWalkthrough` registers what `walkthroughNavigationOf` builds from the page's stepping, filter and file layout. One `keydown` listener in the capture phase runs the control whose key was pressed. It does nothing while a modifier is held, for a repeat, inside an input, textarea, select, contenteditable or text box, or inside a dialog other than a full-screen board (`data-navigator-scope`). Tests render a section in the navigator with `renderInNavigator` of `lib/__tests__/navigator-harness.tsx`, which gives that section a size on screen.
- **No logic beyond rendering.** Pick variants from discriminant props (`kind`, `status`, `severity`). Do not compute them.
- **A part that is not written yet is wrapped in `Unwritten`.** It takes `isPending` from the flag the backend put on the part and reads `WritingContext` (`lib/writing-context.ts`), the one value a component takes from a context instead of a prop: the label of the review's progress while an agent is writing or awaited, `null` otherwise. With both it draws skeleton bars with the label for a screen reader, and an optional `caption` under them; without, it renders its children, which are what the part shows when nobody is writing. The route provides the context once, around the review.
- `src/components/blocks/` holds shadcn building blocks. Add them only with `cd packages/ui && pnpm dlx shadcn@latest add <component>`. Their dependencies go in this package's `package.json`. The CLI writes named exports: make the component the file's default export and fix imports between blocks.
- `src/components/<ComponentName>/index.tsx` holds shared composed components, with tests in `__tests__/` next to them.
- Style with Tailwind classes and the tokens in `src/styles/globals.css`. Use `cn` from `lib/utils` to merge classes. [docs/DESIGN.md](../../docs/DESIGN.md) describes the design system: the tokens, the type, the components and their rules. Follow it, and update it when a component or a rule changes.
- The shadcn blocks are modified to fit the design system. After adding a block with the CLI, restyle it to match: the theme's corners and borders, two font weights, no shadows.
- Icons come from `lucide-react`, which only this package depends on. A control that shows an icon is a component here, and `apps/frontend` uses that component.
- Every file under `src/components/` default-exports its component, and lint enforces it. Consumers import it by its path under `src/components/` (`@flightplan/ui/blocks/button`, `@flightplan/ui/CodeLink`). Inside this package, files import each other through `@/` (`@/components/blocks/button`), which is also what the shadcn CLI writes. There is no package root and no barrel file.
- Components are accessible: semantic elements, labels, keyboard support. `jsx-a11y` strict is enforced.

## Verify

- `nx run-many -t eslint:lint typecheck test -p ui`
- Each component has `@testing-library/react` tests that render it with props and assert on roles, text and callbacks.
- Check changed components in the running app with `agent-browser`, following [testing](../../docs/agents/testing.md#ui-verification-with-agent-browser).
