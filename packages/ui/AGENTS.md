# packages/ui

Flight Plan's component library: shadcn primitives and the shared presentational components that pages compose, such as CodeLink, CodeBlock, Trace Diagram and Blast Diagram. Read [architecture](../../docs/agents/architecture.md) and [react](../../docs/agents/react.md) before changing anything here.

## Rules

- **Props in, JSX out.** Components receive all data and callbacks through props. They never call an API, use tRPC or TanStack Query, read the router, or touch browser storage for domain data.
- **Code is drawn through Code Hike.** `CodeBlock` hands the lines the backend highlighted to `Pre` of `codehike/code` as tokens and annotations, and draws the row, the mark and the definition with annotation handlers. The definitions arrive as its `definitions` prop, and a definition's written description is drawn by its `renderDefinitionDescription` prop, which `FileRows` fills with `HoverProse`, so `CodeBlock` does not import `Prose`. It never calls Code Hike's `highlight`.
- **The rows of a file are drawn by `FileRows` alone.** A File Section of the Code Walkthrough and a code view of a Trace Diagram's side panel both hand their `FileRow`s to `FileRows`, which draws the lines, the rows for hidden lines, the waypoint marks in the gutter with their stems and cards, the open waypoint boxes, the folded root blocks and, when it gets `commenting`, the threads and the composer. `FileSection` adds the file header, and `NodeCodeView` the heading, the path, the range and the note, wraps the lines, turns off commenting, holds which waypoints are open and gives each waypoint an anchor of its own view. Change how code reads in `FileRows`, never in one of them. A pressed mark is held where it was in the nearest scrolling ancestor, the window on the page and the side panel on a board.
- **The Trace Diagram is drawn through React Flow.** `lib/trace-layout.ts` decides where every node, row and line goes: a line that closes a loop moves no node, and is led below the nodes it passes (`withoutLoops`, `pointsBelow`), and `lib/trace-flow.ts` turns that layout into what `@xyflow/react` draws: a node for each plate, with a node inside another as its child, a handle at each end of a line, and an edge for each line that bends where the layout bends it. A line joined to a row is three edges: the line between the two nodes, drawn under the nodes, and the short line to each row, drawn above them. React Flow never arranges anything, and for a reviewer nothing on the diagram can be dragged, connected or selected. An author gets the `authoring` prop: a card at the top level is dragged, a dot at the right of each row starts a line and a dot at the left, the top and the bottom of each card ends one, as does a drop anywhere on a card, which ends the line at the nearest of those sides (`nearestSideOf`), and a drop on the empty board leaves a plus at the end of the line, a node of its own type that is kept in the component and never saved, whose press asks for a card there (`onAddCardAtLineEnd`), a pressed line is selected and removed with a bin on the board's view controls, the Review Navigator adds a card, clears the diagram and removes it with C, K and L (`onAddCard`, `onClearDiagram`, `onRemoveDiagram`), the last two only once the author confirms them in a `ConfirmDialog` the component holds open, and every card has a button to modify it and one to delete it. The component draws and reports, and the page saves. `lib/trace-arrangement.ts` puts the cards with a stored position where it says, stacks the others beside them, and ends a line at the side it reaches. The dots are listed in the `handles` of each node as well as drawn, because React Flow reads the ends of a connection from that list. `DiagramBoard` keeps the zoom and the pan and hands them to `renderCanvas`, where they are the viewport of React Flow. Its zoom in, zoom out and full screen are `IconButton`s in a control group at the top right of the board, sticky below the pinned rows while the board is inline and fixed below the top of the board in full screen, after the `actions` its diagram hands it (the bin of a selected line). It hands the Review Navigator the `groups` of `navigation` that its diagram builds (collapse all, then add card, clear diagram and remove diagram for an author of the Trace Diagram, the views for the Blast Diagram), then a group of its own with full screen (F), and in full screen it draws `ReviewNavigatorBar` inside its dialog. Its stylesheet is imported in `src/styles/globals.css` into the `components` layer, so a Tailwind class overrides it. Tests run with the `ResizeObserver` of `src/lib/__tests__/jsdom-setup.ts`, which React Flow needs and jsdom lacks.
- **The Blast Diagram switches between the views the backend sent.** `BlastBand` takes `views` and `defaultViewId`, holds which view was chosen, and draws that view's counts, key and board. With more than one view it hands a button per view to the Review Navigator, through the `navigation` of `BlastDiagram`: E for the export bound and Q for the import bound, pressed for the view that shows and with the view's `description` as its title. The diagram keeps its zoom and its full screen across a switch, and a selected file that the other view lacks closes the side panel.
- **The Blast Diagram is read-only but for the impact of a file.** `BlastBand` takes `renderImpactEditor`, `null` for a reviewer. For an author the side panel of a file that has an `assessment` shows the form's `editLabel` as a link button, and pressing it draws what `renderImpactEditor` returns in place of the impact reason and the fixed sentence, until the editor calls `onClose`. The component holds which file is being edited and nothing of the form.
- **A form that more than one page draws takes its actions as `children`.** `AgentsForm`, `ForgesForm` and `ReviewConfigurationForm` hold the fields and what the user chose, call `onSubmit` with the choice, and render their `children` at the foot of the `<form>`, where the page puts its submit button. They show a `FormProblem` (`lib/form-problem.ts`) under the field it names; the page shows one that names no field. `ReviewConfigurationForm` is every part of the setup's Review configuration step, each part a section with an `h3`; a part with more than plain inputs is a controlled field component of its own (`SpotlightField`), and the form is generic over the classification type, so what it submits matches the backend's input.
- **The Review Navigator shows the controls of the section on screen.** `ReviewNavigator` wraps a review page, takes its `rail`, and works out which rail section is most present on screen: the larger of its share of the window and the share of itself in view. A section registers its controls under its anchor with `useNavigatorSection(anchorId, groups)`, built from `navigatorButtonOf`, a `menu` of checkbox choices and submenus of them, or a `position`, and `ReviewNavigatorBar` draws Jump to, then Back (A) and Next (D) to the rail sections around the one on screen (`sectionStepsOf`), then those groups. A section that registers a control for A or D takes that key from Back or Next (`withSectionSteps`); `CodeWalkthrough` does so, and puts the step `useSectionSteps` gives it in place of its waypoint step at the ends of its segment. `ContextBand` registers through `useAccordionNavigation`, which also holds which accordion sections of `Prose` are open through `AccordionOpeningContext`; `DiagramBoard` registers the controls its diagram hands it; `CodeWalkthrough` registers what `walkthroughNavigationOf` builds from the page's stepping, filter and file layout. One `keydown` listener in the capture phase runs the control whose key was pressed. A control's key can be a Control chord such as `ctrl+g` (`navigatorKeyOf` in `lib/navigator-keys.ts`), the one modifier it reads; it does nothing while Cmd or Alt is held, for a repeat, inside an input, textarea, select, contenteditable or text box, or inside a dialog other than a full-screen board (`data-navigator-scope`). Tests render a section in the navigator with `renderInNavigator` of `lib/__tests__/navigator-harness.tsx`, which gives that section a size on screen.
- **No logic beyond rendering.** Pick variants from discriminant props (`kind`, `status`, `severity`). Do not compute them.
- **A part that is not written yet is wrapped in `Unwritten`.** It takes `isPending` from the flag the backend put on the part and reads `WritingContext` (`lib/writing-context.ts`), the one value a component takes from a context instead of a prop: the label of the review's progress while an agent is writing or awaited, `null` otherwise. With both it draws skeleton bars with the label for a screen reader, and an optional `caption` under them; without, it renders its children, which are what the part shows when nobody is writing. The route provides the context once, around the review.
- `src/components/blocks/` holds shadcn building blocks. Add them only with `cd packages/ui && pnpm dlx shadcn@latest add <component>`. Their dependencies go in this package's `package.json`. The CLI writes named exports: make the component the file's default export and fix imports between blocks.
- `src/components/<ComponentName>/index.tsx` holds shared composed components, with tests in `__tests__/` next to them.
- Style with Tailwind classes and the tokens in `src/styles/globals.css`. Use `cn` from `lib/utils` to merge classes. [docs/DESIGN.md](../../docs/DESIGN.md) describes the design system: the tokens, the type, the components and their rules. Follow it, and update it when a component or a rule changes.
- The shadcn blocks are modified to fit the design system. After adding a block with the CLI, restyle it to match: the theme's corners and borders, two font weights, no shadows.
- Icons come from `lucide-react`, which only this package depends on. A control that shows an icon is a component here, and `apps/frontend` uses that component.
- Every file under `src/components/` default-exports its component, and lint enforces it. Consumers import it by its path under `src/components/` (`@flightplan/ui/blocks/button`, `@flightplan/ui/CodeLink`). Inside this package, files import each other through `@/` (`@/components/blocks/button`), which is also what the shadcn CLI writes. There is no package root and no barrel file.
- Components are accessible: semantic elements, labels, keyboard support. `jsx-a11y` strict is enforced.

## Verify

- `nx run-many -t eslint:lint typecheck test -p ui`
- Each component has `@testing-library/react` tests that render it with props and assert on roles, text and callbacks.
- Check changed components in the running app with `agent-browser`, following [testing](../../docs/agents/testing.md#ui-verification-with-agent-browser).
