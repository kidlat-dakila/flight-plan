# packages/codegraph

The pipeline that traces a change through the code, and the builders that turn a change into the parts of a review artifact and the bands the review page renders. Read [codegraph](../../docs/vocabulary/codegraph.md) before changing anything here.

## Rules

- **One entry.** `src/index.ts` is the only module another project imports, as `@flightplan/codegraph`. The package is consumed as source and has no build step. It is marked `"sideEffects": false`, so the backend's bundle keeps only what the backend calls.
- **Shapes come from `packages/configurations`.** The artifact's types and the band schemas are imported from `@flightplan/configurations`, never declared here. A builder's own input types live beside it: `ReviewViewContext` and `BlobLinker` in `review-view-context.ts`, `ReviewedMarks` in `walkthrough/reviewed-marks.ts`, `DiagramSettings` in `journey/filter.ts`.
- **A builder is a calculation.** Every builder takes plain data and returns new data. What only the backend knows arrives as an argument: forge links as a `blobLinkOf` function, the lines a comment thread pins as a `pinnedLinesOf` function, highlighted code as `HighlightedSource`. A builder never reads a discussion, a store or a forge.
- **The import graph reads through git-forge.** `src/import-graph/` answers who imports a file and what it imports, at one commit of a change. `createImportGraphContext({ gitAdapter, baseCommit, headCommit })` reads a change once, and `traceImportGraph(context, filePath)` traces one file through it in both directions. Every file, file list and search comes from the `GitAdapter`: `blobs`, `listFiles` and `searchFiles`. A changed file is traced at the head commit and a deleted file at the base commit. Each traced file carries `importedFilePaths`, the file every import specifier in it resolves to, whether that file is in the trace or not; `importsTo` lists only the files inside the trace. A Python import is named by `pythonSpecifierOf`: its module as written, then `:` and the name taken from it. `clusterImportGraphs(importGraphs)` joins the traces that share a file into one cluster, so a cluster is one connected part of one language.
- **An importer is searched for, then proven.** A language in `import-graph/languages/` gives the patterns an importer of a file would contain, `searchFiles` finds the candidates, and a candidate counts only when one of its imports resolves to the file. Dynamic `import()` calls are not imports.
- **A file of the AST graph is built once.** `src/ast-graph/languages/base.ts` holds `BaseASTGraphFile`, which every language extends. Its constructor takes a parsed tree and extracts the root encapsulations, the variables, the import variables and the references, and nothing changes them afterwards. It also takes `diffLines`, the line ranges the change touches in the file, and places them as `DiffLocation`s: a range of changed lines, the root encapsulation it lies in and the nearest encapsulation that holds it. A location belongs to one root encapsulation, so a range that spans several, such as the whole of a new file, is split into one location per root encapsulation and cut to its lines. Changed lines outside every root encapsulation have no location. A language implements the eight `extract…` methods from the tree it is handed and never reads its own fields in them, because the base constructor runs them first: root encapsulations, file variables, import variables, references, export aliases, re-exports, syntax sites and statements.
- **A group of the AST graph is one cluster of the import graph.** `ast-graph/ast-code-group-graph.ts` holds `ASTCodeGroupGraph`. Its constructor takes the files of a cluster with their source text and builds one file of the AST graph for each, with the class `languages/create-ast-graph-file.ts` picks from the file's extension; a file no language reads is left out. `readASTCodeGroupGraph({ gitAdapter, importGraph, diffLines })` is the only part that reads: it fetches the sources with one `blobs` call per commit. `traceDeepUsageFromAstGraphFile(astGraphFile, diffLocation)` returns the `DiagramNode` of the location's nearest encapsulation with its callers, and `traceAllDiffUsage()` returns one tree per changed encapsulation of the group.
- **A deep trace climbs through uses.** `ast-graph/trace-deep-usage.ts` asks the file of an encapsulation for the uses of its name, asks every file of the group for the uses of the names the file exports it by, and makes the nearest encapsulation of each use a caller, once, at its first use. It climbs from each caller the same way and never enters an encapsulation already on the path. A use outside every encapsulation gives no caller. The group never reads syntax: what a name is, who exports it and who uses it are answered by the files.
- **An encapsulation without a name of its own is traced through the one that holds it.** A method is not a variable, so its uses are the uses of its class, and its node is named `Class.method`. A root encapsulation is known to importers by its own name and by every export alias of that name: `default` for `export default function priceOf`, `price` for `export { priceOf as price }`.
- **A name is handed on only where it is exported.** A file hands an imported symbol on under the names it exports that import by, and under the names of its re-exports: `export { a as b } from`, `export * from`, which keeps every name but `default`, and `export * as ns from`. Python exports every name it imports. A namespace import counts as a use of a symbol only in a file that imports the symbol's own file, not one that reaches it through a re-export.
- **A change outside every encapsulation is a loose statement.** A top-level statement that no root encapsulation shares a line with (an import, a type, an interface, a bare call) is loose. `listLooseDiffLines()` gives the whole line range of every loose statement the diff touches, joined when they follow each other; when a file's changed lines are in no encapsulation and no statement at all, it gives the changed lines themselves, so a changed file is never without a place. `traceLooseDiffUsage()` traces each one to the uses of what it declares and names its node after those names, or `Lines 3–5` when it declares none. `traceLooseDeclarationUsage()` keeps only the ones that declare a name.
- **The pipeline is `buildCodegraph`, and it lives in the entry.** `src/index.ts` holds it, beside the re-exports of the builders the backend calls. `buildBranchCodegraph({ gitAdapter, ref })` is where a caller starts: it takes a branch or a pull request, asks the adapter for its `baseSha` and `headSha`, and hands the two commits to `buildCodegraph`. It reads a change through git-forge once: it traces and clusters the import graph, reads the changed lines of each file from the patches of the comparison with `diffLinesOf` (`src/diff-lines.ts`), and builds one segment per cluster: `{ importGraph, astGraph, journeyFlowDiagram, blastRadiusDiagram, codeWalkthrough, codeReferences }`. A deleted file has no changed lines. Lines that were only removed count as a change on the line before them.
- **Shared plumbing has one home.** `src/shared/` holds what the folders share: `Memo` and `once` (`memo.ts`), `groupBy` (`group-by.ts`), `recordOf` and `omit` (`record.ts`), `mapInSequence` (`sequence.ts`) and `firstOfEach` (`first-of-each.ts`). The module resolvers of the import graph are in `import-graph/languages/`: `typescript-resolve.ts`, `python-module-roots.ts` and `python-resolve.ts`.
- **The generators import only `ast-graph/`, `import-graph/`, `shared/` and `@flightplan/configurations`.** `src/journey-flow-diagram/`, `src/blast-radius-diagram/`, `src/code-walkthrough/`, `buildCodegraph` in `src/index.ts` and `src/diff-lines.ts` take nothing from `src/scaffold/`, `src/journey/`, `src/blast/` and `src/walkthrough/`. The trees they read are `DiagramNode`s of `ast-graph/diagram-node.ts`.
- **Trees are merged into one graph before they are drawn.** `mergeDiagramNodes` in `ast-graph/usage-graph.ts` lists every declaration of the trees once, named by its file and its name, with one edge from each user to what it uses, and marks the root of every tree as changed. Two changes on one chain therefore share a diagram. The Blast Diagram's generator starts from it.
- **A journey is traced from the files, not from the trees.** `generateJourneyFlowDiagram(astGraphFiles)` returns one `JourneyFlow` for a segment, or `null` when no code that runs changed. `journey-flow-diagram/trace.ts` starts at every changed encapsulation and climbs through its uses to what triggers it. A node is a root encapsulation: a change inside a nested function or a method belongs to the node of the root that holds it. Nothing is traced downward, so a path ends at its last change. A use in an export list, an import or a type is not a use.
- **One trace serves every language, and JSX differs only through its syntax sites.** Nothing in `journey-flow-diagram/` asks whether a group holds JSX. A JSX file gives `attribute`, `element`, `markup` and `page` sites and `markup` statements, and those are what produce handler nodes, context readers, route visits and traced lines through markup. A file without them is traced by its calls alone.
- **A use has a role, and the role decides the climb.** `journey-flow-diagram/usage-role.ts` reads the syntax sites around a use, the narrowest first: a call or a render makes the encapsulation that holds it the next node; a handler on a built-in element ends the path at a user action; a prop on a component is followed into that component (`resolve-props.ts`), to where the prop is run, whether the component reads it from its parameter, takes it apart in its body (`const { onSave } = props`) or keeps it in a variable of its own; a page in a route table (`element` or `component` beside a `path`, a `<Route>`, a file route) ends at the visit of that route, named with its whole path; a route registration ends at an API call, a subscription (`on`, `once`, `addListener`, `subscribe`) at an event bus, a function handed to `addEventListener` at a user action named after its event and the object it listens on; a `Provider` value is followed to the components that read the context (see below); a function handed to a call whose result is kept takes its entry point from where that result is used. A use at the top level of a file ends the path at the entry point its syntax names.
- **A change inside a member is traced through the uses that take that member.** A changed action of a store, or any member without a declaration of its own, is followed only through the uses of its holder that name it on the same line, such as `useCartStore((state) => state.addItem)`, and then through what keeps the result. When no use names the member, every use of the holder counts. Every nested encapsulation a changed range touches is a starting point, so a hunk that covers a handler and the lines around it still starts at the handler.
- **A context is followed to the components that read it.** `journey-flow-diagram/context-readers.ts` finds the uses of the context handed to `useContext` or `use`. A reader that keeps the whole value is followed through that value; a reader that takes the value apart is followed only through the member with the name of what was provided, and through every member when the provided value reached the `Provider` through a call such as `useMemo`. From there the result is traced like the result of a hook: called from a handler it ends at a user action, read in the render body at a page visit. The reader has a `value` edge to the encapsulation that renders the `Provider`. When no reader takes it, the path ends at the `boundary` entry `Reached through a context`.
- **An entry point carries where the trace ended.** An `EntryFact` has an `end`: the file and the range of the handler attribute, the listener, the route, the page site or the last use, with the event, the element and, for a component imported from outside the repository, the import specifier (`findExternalImportSpecifier`). `generateJourneyFlowDiagram` stores it as the node's `traceEnd`, with the line and its source. The entry point of changed bare statements has none.
- **A user action leads to a node for its handler, not to the component.** `generateJourneyFlowDiagram` gives every entry point with an `actedAt` (a handler attribute, or a listener inside an encapsulation) a Code Node of its own. Its ranges are the attribute or listener and the functions declared in the component that run at it; an edge whose use lies in those ranges leaves from the handler node, and the trigger edge arrives at it. An edge to the result of a hook is one fact per use of the result (`keptAt` is the call that keeps it), so a result used in a handler leaves from the handler node and a result read in the body from the component. Where the handler runs a prop, the node moves to the component that hands the handler over (`handedAt` on the edge, set where the trace follows a prop): the entry point then leads to `CartPage.handleCheckout`, and the trigger edge's `through` lists `Button.onClick` and the props between. A handler node is named `<component>.<handler or attribute>`, has the id of its component with the event and the line, is changed when a changed line overlaps its ranges, and its `tracedLines` are the element acted on and the handler. A component is a changed node only when a changed line lies outside every handler range that spans more than one line.
- **An entry point with no node under it is left out.** `generateJourneyFlowDiagram` keeps an Entry Point Node only when its trigger edge arrives at a node that is drawn. An entry point with one Code Node under it and nothing else is a path and is drawn.
- **A component is the only `ui` node and a handler node the only `event` node.** `toDeclarationNode` in `journey-flow-diagram/index.ts` gives `ui` to a root encapsulation that `isComponent` of `entry-points.ts` accepts (a capitalised name or a default export, with markup inside) and `logic` to every other encapsulation: a function, the top level of a file, a constant that holds markup. `toActionDeclarationNode` gives `event` to every handler node. The two are `GENERATED_NODE_CATEGORIES` in `packages/configurations`: the backend's `amend-journey.ts` refuses an agent's edit that writes or replaces one, and the playground's `written-parts.ts` keeps the generated one over a snapshot's.
- **A node says how it stands to the diff with `changeType`.** A Code Node is `diff` when a changed line is on it and `related` otherwise, since an unchanged node is only drawn on the way to a change; it is never `none`. `isChanged` is left on a traced line only.
- **A value read in markup is absorbed into the component's data.** In `generateJourneyFlowDiagram`, an edge is a data read (`isDataRead`) when it leaves a component, its use is one of `listDataReads` of that component, and it arrives at an encapsulation of the kind `variable` or is the read of a hook's result (`keptAt` is set). A site at least one data read arrives at, that every other edge into is the read of a hook's result by a component (`isAbsorbable`), that no entry point leads to and that no edge leaves from is in `listAbsorbedSiteIds`: it gets no node and no edge. A handler node that is unchanged and has no edge left is dropped with its entry point (`leadingActions`). The read is `related` in the component's `data` when the site is changed, and a diagram whose only change is absorbed is headed by the components that read it. `journey/filter.ts` treats such a component as a head.
- **A `ui` node lists its events and its data.** `journey-flow-diagram/traced-names.ts` reads them from the syntax sites and the value references inside the component: `listTracedEvents` gives one entry per callback attribute (an `on…` name, a function written in place, or a function declared in the component) and per `addEventListener` argument, and `listTracedData` one per variable read inside a `markup` site, without element names, plain callees, variables declared inside the markup and what lies in a callback attribute. An entry is `{ name, changeType, reference }`, where `reference` is a line tuple and `changeType` is `diff` when a changed line is on the entry, `related` when one is on the function declared in the component that an event hands over or on the declaration statement of a variable inside the component, and `none` otherwise. The link never leaves the component. An entry of `events` also carries `nodeId`, the id of the drawn handler node whose ranges hold the attribute or the listener, or `null`. Every other node has both lists empty.
- **A component with several returns lists them.** `journey-flow-diagram/component-returns.ts` reads the `return` statements of a component's own body from its statements: it descends through conditionals, loops and `try` blocks, and never into a declaration, an expression or markup, so a `return` of a nested function or a callback is not one. With two or more, `listComponentReturns` gives one `ComponentReturn` each, in source order: an id (`<node id>#return@<line>`), the `statement` (the first line up to and including `return`), its lines, `diff` or `none`, the traced lines up to the end of the return, and `renderedNodeIds`, the nodes of the render edges whose use lies in the return, in reading order. A component with one return, and every node that is not a component, has `returns` empty.
- **An Entry Point Node says what triggers the path.** `journey-flow-diagram/entry-points.ts` holds the triggers and their labels: `page-visit`, `user-action`, `api-call`, `command`, `boundary`, `app-start` and `unused`. Every path has one. A changed handler written in place on a built-in element gives its handler node a user action of its own.
- **An unchanged encapsulation that only forwards is a step on the edge.** A component that passes a prop on, and a function whose whole body is one call, are not nodes: their names are the edge's `through`. A changed encapsulation is always a node, and so is one the path would otherwise end on.
- **A node carries its traced lines, and an edge carries none.** `journey-flow-diagram/traced-lines.ts` lists the source lines a debugger would step through in a root encapsulation: a statement on the way with every line it spans, a branch, a loop or an inner function the path does not go into by its first lines only, and nothing after the target. In a JSX file an element is a statement of the type `markup`, nested under the element that holds it, so the lines step into the elements above a hand-over and stop at it. A node's `tracedLines` run to its changed lines, or to where the path leaves it when the diff did not touch it. They are how the inside of a node is shown without more nodes: a branch or a `.map` of a component is lines of that component. Changed bare statements at the top level of a file are one node named `top level`, whose traced lines are those statements. A changed import or type gives no node.
- **The band groups the components into UI cards.** `journey/ui-cards.ts` builds one tree per top-most `ui` node from the edges between two `ui` nodes, repeats a component under every parent, and lays each tree out as frames and trigger rows with fixed sizes; an event node no row leads to gets a card of one frame. `journey/layout.ts` gives `layoutLayers` one box per card and one per node outside a card, draws no edge between two nodes of a card, and ends every other edge at the port of its row (`listCardPorts`): the right edge of the card for a line that leaves, the left edge for one that arrives. `journey/layered-layout.ts` places the boxes: a box is one column after the last box that leads to it, a box nothing leads to is one column before the first box it leads to, the boxes of a column are ordered by the height of the ports and boxes they connect to and moved as close to level with them as the gap between two boxes allows, and the gap between two columns grows with the steepest line that crosses it. An edge is straight lines only: level across a column, slanted between two columns, and an edge that skips a column crosses it level in a lane of its own between the boxes. An edge is drawn once per place its node is drawn, with `#1`, `#2` after its id. A component with `returns` is laid out as its returns: `toFrameTree` turns it into a frame of the role `group` that holds one frame of the role `return` per return, and each return frame holds the data and the triggers on its lines and the children in its `renderedNodeIds`. A component that another component renders is a `group` too, whatever its returns: with none in `returns`, the group holds one frame of the role `return` that stands for the whole component, with `componentReturn` `null`. A `group` at the top of a card is not a frame: its return frames sit in the card, the card's `headerNode` is the component, and the component's port is the card's header (`headerPortsOf`). A return frame has no port. The band carries the cards as `uiCards`, and a node or an edge drawn inside one has `isInsideCard`. `journey/build.ts` adds one node of the kind `return` per return frame, so that choosing the frame opens the return's label, description and traced lines; a frame's `nodeId` is what it opens and its `ownerNodeId` is the component it is hidden with. An edge of the band has its two ends and its points only: the page draws every edge as the same line with no label, and the `kind`, `certainty` and `through` of the stored edge stay in the artifact for the agent.
- **A node says which code is read beside it.** `journey-flow-diagram/code-views.ts` gives every Code Node and every return of a component its `codeViews`: a `kind`, a `path`, the `lines` as line spans, the `marks` as single-line column spans in reading order and an `entryCount`. A node that is not a component has one `declaration` view of its whole root encapsulation, and the top level of a file one of its changed statements. A component has a `data` view per file a value it reads in markup is declared in, with a mark on the declared name; one `event` view of every callback attribute and listener, each from the line its element starts on to the end of the attribute, with the functions the component declares for it and a mark on the attribute; and one `render` view of its `return` statements, or of the whole component when it has none. A return has the `data` and the `event` views of what lies on its lines, then its own `render` view. A handler node has one `event` view of its attribute and the handlers run at it. `journey-flow-diagram/return-statements.ts` lists the `return` statements both the returns and the views read.
- **A name is looked up once, for the views and for the page.** `ast-graph/definition.ts` holds `findDefinition(files, file, target)`: a name declared in the file leads to the lines of its root encapsulation, or of the narrowest `import`, `type` or `declaration` statement that holds it, or to its own line for a parameter; an imported name leads to the lines the file it comes from exports it by, through re-exports, and to its import statement when it comes from a library, from a namespace import or from a file outside the group. `generateCodeReferences(astGraphFiles, paths)` in `code-references/` lists, for each path, every single-line use with its columns, the `path` and `lines` of its definition and `isLibrary`, and leaves out a use that lies on the lines of its own definition. `buildCodegraph` asks it for the files of the Code Walkthrough and of the code views, and a segment carries the result as `codeReferences`.
- **The band turns code views into rows.** `journey/code-views.ts` gives a node of the band one `NodeCodeView` per stored view whose file has a source: a heading, a count label, the path, the range, a note for a file outside the segment's `changedPaths`, the link, and `rows` of the walkthrough's row shapes. A span is a `lines` row read from the source as the Code Walkthrough reads it, two spans are divided by a `gap` row, and a `waypoint` row with the waypoint's own view stands before the first span that overlaps its range. `listWaypointPlaces` in `walkthrough/build.ts` gives the visible waypoints with their ranges, and the caller hands them to `buildJourney`. A node with no code view keeps its `codeLinkId`, and the page then shows its whole declaration.
- **A line carries its marks and the definitions it leads to.** `codeLinesIn` in `code/lines.ts` takes `LineDecorations`: the marks of a view, the line spans shown with it and the ids of the known definitions. A line gets the marks on it and the references of its source file in columns that start at one and end on the last character. A reference is left out when its definition is not known or lies on the lines shown. `buildCodeDefinitions` in `code/definitions.ts` builds one definition per reference target that has a source, keyed by `definitionIdOf`, with a note for a library, and draws its lines with no references. The Code Walkthrough passes the lines of every row it shows as the lines shown.
- **A file answers the syntax the journey reads.** A language implements two more extractions: `extractSyntaxSites` gives the attributes, arguments, callees, members, elements, functions and kept values of a file as `SyntaxSite`s, and `extractStatements` gives its statements nested with their arms. `languages/typescript/syntax-sites.ts` and `statements.ts` read them, `languages/jsx/syntax-sites.ts` adds the element sites, and `languages/nest-statements.ts` nests statements and arms by what contains what. Python and Vue give none yet, so their journeys have plain call edges, no traced lines and no named triggers beyond a route file's and `unused`.
- **A blast is never left out.** `generateBlastRadiusDiagram(segmentDiagramNodes)` always returns a `Blast`. A node's ring is its distance to the nearest change. `buildCodegraph` hands it the trees of the changed encapsulations and of the loose statements that declare a name, so a changed type is an Epicenter Node with its users around it; when both are empty it hands over every loose change, so a segment with any change has an Epicenter Node.
- **A waypoint knows its kind and its nodes.** `generateCodeWalkthrough` makes one File Section per file with changes and one waypoint per changed declaration: the function a change is in, the method when the function is inside a class, or a loose statement. Each waypoint carries its line `range`, a `category` read from the syntax tree (`function`, `class`, `method`, `variable`, `import`, `type` or `statement`), the `journeyFlowId` and `journeyNodeId` it belongs to and its `blastNodeId`, each `null` when the diagram has no node for it. These fields are declared in `code-walkthrough/` as `LinkedWaypoint`; the stored artifact in `packages/configurations` does not have them.
- **A language of the AST graph has its own folder.** `ast-graph/languages/typescript/` holds `TypescriptASTGraphFile` in `index.ts` and one module per extraction beside it: `encapsulations.ts`, `declarations.ts`, `imports.ts`, `references.ts` and `exports.ts`, with `scopes.ts`, `patterns.ts` and `syntax.ts` under them. The class reads trees of the `typescript` grammar. Each extraction asks the tree for the node types it reads with a tree-sitter query, through `nodesMatching` in `ast-graph/query-nodes.ts`, and does not visit the other nodes. `languages/nest-encapsulations.ts` nests the encapsulations a language found by what contains what.
- **JSX is TypeScript with elements.** `ast-graph/languages/jsx/` holds `JSXASTGraphFile`, which reads trees of the `tsx` grammar: `.tsx`, `.jsx` and plain JavaScript files. It reuses the TypeScript extractions and adds the element rules in `jsx/references.ts`: an element whose name starts with a capital, or that is a member such as `<Form.Field>`, is a use of that name, counted once at its opening tag. A lowercase element, a namespaced element and an attribute name are not uses. The specs in `typescript/__tests__/` run every TypeScript case against both classes through `SCRIPT_DIALECTS` in `languages/__tests__/script-files.ts`.
- **Python binds names, it does not declare them.** `ast-graph/languages/python/` holds `PythonASTGraphFile`. `bindings.ts` reads every place a name is bound (a `def`, a `class`, a parameter, an assignment target, a loop, `with`, `except`, `:=`, a `match` capture, a type parameter, an import) and keeps the first one in each scope as the declaration; a later binding of that name in that scope is a use. A scope is the body of a function or lambda, a comprehension, or the file. There is no block scope, `global` and `nonlocal` move a binding to the scope they name, and what a class body binds is neither a variable nor a use, because a method cannot see it. Every import of a name is kept when its first binding is an import, so `import shop.tax` and `import shop.pricing` both count.
- **A Python import of a name may be a module.** `from shop import pricing` has the imported name `*` when the file it resolved to is the module `pricing`, and `pricing` when the file is the package that defines it.
- **A Vue file is three languages.** `ast-graph/languages/vue/` holds `VueASTGraphFile`, which takes the tree of the whole file parsed with the `html` grammar (`tree-sitter-html`). `sfc.ts` finds the script blocks and the template in it. `script.ts` parses each script block with the TypeScript grammar its `lang` names and reads it with the TypeScript extractions. `template.ts` parses every expression of the template (an interpolation, a bound attribute, a handler, the two sides of a `v-for`, the properties of a slot) as a snippet of TypeScript. `snippet.ts` moves what a snippet found to its lines and columns in the file.
- **A Vue component is the default export.** A `<script setup>` block and the template are each a root encapsulation named `default`, and a file that does not export a default declares the variable `default`, so an importer's default import leads to them. The top level of a setup script is seen by the template, the top level of a script without setup is not. A `v-for` variable and a slot property are seen inside their element only. A capitalised tag, a tag with dashes and the object of a member tag are uses of the component's name, and `v-focus` is a use of `vFocus`.
- **A name is resolved once per space.** A declaration and a use each carry the spaces they live in, `value`, `type` or both, so `const Cart` and `type Cart` in one scope stay apart. A use belongs to the declaration of its name with the nearest scope in each of its spaces, and to every such declaration when several share that scope. A class, an enum, a namespace and an import are in both spaces.
- **An encapsulation is something a changed line can belong to.** At the root of a file that is a function, a class, a variable, an enum, a namespace or a default export. Below the root it is a function, a class, a method, or a variable, field or member of a declared object that holds a function or a class. Types, declarations marked `declare`, overload signatures and the members of an object handed to a call or to an element are not encapsulations. An object handed to `defineComponent` is the exception: its members are.
- **Every parse goes through `ast-graph/parser.ts`.** It parses with the native `tree-sitter` package and the `tree-sitter-typescript`, `tree-sitter-python` and `tree-sitter-html` grammars, keeps one parser per grammar and the compiled queries, and is the only module of `ast-graph/` and `import-graph/` that holds state. Parsing is synchronous and a tree is freed by the garbage collector.
- **The import graph reads git in batches.** A trace asks for the importers of every file of a level in one `searchFiles` call, and reads the files of a level in one `blobs` call through `RepositorySnapshot.preload`. Code in `import-graph/` never searches or reads once per file in a loop.
- **A tree is walked with a cursor.** `ast-graph/walk-tree.ts` holds `collectFromNode`, which visits the nodes under a node through a tree-sitter `TreeCursor`. Code in `ast-graph/` walks with it, never with a recursive read of `children`.
- **The end-to-end cases live in another project.** `tools/playground-fixtures` holds the cases that run `buildBranchCodegraph` against whole repositories, and their snapshots. A change to what the codegraph produces changes those snapshots: run `nx test playground-fixtures`, and `nx run playground-fixtures:snapshot` after an intended change. A segment of the codegraph has a `title`, `null` until a case or a consumer writes it.
- **A rule has a fixture.** Every rule has a test in the `__tests__/` folder beside the code that implements it.

## Layout

```
src/import-graph/ the files a file imports and is imported by, traced through git-forge, with one module per language in languages/
src/shared/       the plumbing the folders share: a cache, grouping, records, running in order
src/ast-graph/    the encapsulations, variables and uses inside one file, with one class per language in languages/<language>/
src/journey-flow-diagram/  the files of a segment → its Journey Flow Diagram: the trace, the roles of a use, the entry points, the traced lines, the events and the data of a component
src/blast-radius-diagram/  the trees of a segment → its Blast Diagram
src/code-walkthrough/      the files of a segment and its two diagrams → its Code Walkthrough
src/code-references/       the files of a segment → where each name used in the viewed files is defined
src/scaffold/     a change's diff and files → the first review artifact: hunks, declarations, File Sections and waypoints, source lines
src/code/         source lines with their marks and references, code links, code definitions, highlighting a review, marked source for fixtures
src/prose/        Markdown prose → the prose shapes, and count labels
src/diagram/      what both diagrams share: the settings, levels through edges
src/journey/      Journey Flow Diagram: filter, layout, code views, band
src/blast/        Blast Diagram: filter, shields, layout, band
src/walkthrough/  Code Walkthrough: waypoints, reviewed marks, file rows, band and controls
```
