# packages/codegraph

The pipeline that traces a change through the code, and the builders that turn a change into the parts of a review artifact and the bands the review page renders. Read [codegraph](../../docs/vocabulary/codegraph.md) before changing anything here.

## Read before you work

The rules below hold for the whole package. A folder with a guide of its own adds rules for that folder:

## Rules

- **One entry.** `src/index.ts` is the only module another project imports, as `@flightplan/codegraph`. The package is consumed as source and has no build step. It is marked `"sideEffects": false`, so the backend's bundle keeps only what the backend calls.
- **Shapes come from `packages/configurations`.** The artifact's types and the band schemas are imported from `@flightplan/configurations`, never declared here. A builder's own input types live beside it: `ReviewViewContext` and `BlobLinker` in `review-view-context.ts`, `DiagramSettings` in `diagram/settings.ts`. `ReviewedMarks` and the reviewed calculation come from `@flightplan/reviewed-marks`, which the published copy runs too: `walkthrough/reviewable-file.ts` builds the outline of a file it reads (its waypoints and root code blocks, with their ids and fingerprints), and the walkthrough builder asks `reviewedStateOf` what the marks make reviewed.
- **A builder is a calculation.** Every builder takes plain data and returns new data. What only the backend knows arrives as an argument: forge links as a `blobLinkOf` function, the lines a comment thread pins as a `pinnedLinesOf` function, highlighted code as `HighlightedSource`. A builder never reads a discussion, a store or a forge.
- **The pipeline is `buildCodegraph`, and it lives in the entry.** `src/index.ts` holds it, beside the re-exports of the builders the backend calls. `buildBranchCodegraph({ gitAdapter, ref })` is where a caller starts: it takes a branch or a pull request, asks the adapter for its `baseSha` and `headSha`, and hands the two commits to `buildCodegraph`. It reads a change through git-forge once: it traces and clusters the import graph, builds the groups of code blocks with `readCodeGroups`, which also reads the manifests of the repository and keeps the syntax of each file beside its group, cuts each group with `cutSegments`, and builds one segment per cut: `{ kind, importGraph, journeyFlowDiagram, blastRadiusDiagram, codeWalkthrough, codeReferences }`. A changed file no cluster holds, such as a migration, is a group of its own. A segment whose group holds only `file` blocks, which no language reads, is drawn into the shared segment of the change, after its files (`withUnreadInShared`), and is a segment of its own when the change has no shared segment. A deleted file has no blocks: it is with the first segment of its cluster, or alone in a segment when its cluster has no group.
- **A requested review is the codegraph of its branch, assembled.** `buildBranchReviewArtifact({ gitAdapter, ref, title, newId })` in `src/index.ts` runs the pipeline once and returns a drafting `ReviewArtifact` with the commit the branch started from. It reads the hunks of each file from the patches the import graph context already holds (`hunkOfPatch`), reads the head text of every changed file and of every file a journey or a code reference shows with one `blobs` call, and hands both to `assembleReviewArtifact` in `scaffold/review-artifact.ts`. That calculation maps a segment of the codegraph to a segment of the artifact, drops the fields of a `LinkedWaypoint` the stored artifact does not have, and builds each source file with the declaration of every waypoint on its lines. `tools/playground-fixtures` assembles a snapshot through the same function, so a fixture and a requested review cannot differ in shape. It is the one function of the entry that reads `src/scaffold/`; `buildCodegraph` still takes nothing from it. `buildCommitReviewArtifact` is the same build between two commits the caller names, which is what `buildBranchReviewArtifact` calls once it has asked the adapter for them, and what the backend calls to build a diagram of a stored review again at the commits that review compares.
- **Shared plumbing has one home.** `src/shared/` holds what the folders share: `Memo` and `once` (`memo.ts`), `groupBy` (`group-by.ts`), `recordOf` and `omit` (`record.ts`), `mapInSequence` (`sequence.ts`) and `firstOfEach` (`first-of-each.ts`). The module resolvers of the import graph are in `import-graph/languages/`: `typescript-resolve.ts`, `python-module-roots.ts` and `python-resolve.ts`.
- **Every cluster is drawn from code blocks.** TypeScript, JavaScript, JSX, Vue and Python each have a language in `code-blocks/languages/`, and a file none of them reads is one `file` block. A file is parsed once: the language that reads its blocks also reads its syntax, and `buildCodegraph` builds the files of the AST graph of a cluster from it with `listASTGraphFiles`, which `generateCodeReferences` reads the names from. `buildCodegraph` links each group once with `linkCodeGroupGraph`, and `generateJourneyFlowDiagram` draws every segment of a group from that one group in memory, so the diagrams of two segments hold the same blocks.
- **The generators import only `ast-graph/`, `code-blocks/`, `import-graph/`, `shared/` and `@flightplan/configurations`.** `src/journey-flow-diagram/`, `src/blast-radius-diagram/`, `src/code-walkthrough/`, `buildCodegraph` in `src/index.ts` and `src/diff-lines.ts` take nothing from `src/scaffold/`, `src/journey/`, `src/blast/` and `src/walkthrough/`.
- **A line carries its marks and the definitions it leads to.** `codeLinesIn` in `code/lines.ts` takes `LineDecorations`: the marks of a view and the ids of the known definitions. A line gets the marks on it, the references of its source file and the names of its exports, in columns that start at one and end on the last character. A reference is left out only when its definition is not known, so a name whose definition is on the lines shown leads to it too. `buildCodeDefinitions` in `code/definitions.ts` builds one `declaration` definition per reference target that has a source, keyed by `definitionIdOf`, with a note for a library: its lines are the lines of the target as the change leaves them, without a removed line, drawn with no references. It builds one `usages` definition per export of a source, keyed by `usagesDefinitionIdOf`: the exported name, the count of its usages and files, and each file that uses it with its usage lines, each usage marked and drawn with the tokens `highlightReview` gave its line (`usageTokenLines`), or the note that no file imports it.
- **The context code blocks are listed when the artifact is assembled.** `listContextCodeBlocks` in `scaffold/context-code-blocks.ts` takes the segments and returns the items a description can be written for, each with no description and `isRequired: false`. Code of the repository: every root block of a file a waypoint or a journey node shows, and every block an `external-block` symbol of a block of such a file names, without the `import`, `root-statement`, `file` and `deleted` blocks, once by block id, in the order of path and first line. Libraries: one item per `library` of the segments' code references, with the import block on the reference's lines. Language: one item per name of the segments' `languageReferences`, with no block. `contextIdOf` gives an item its id: the block's id, `library:<specifier>#<name>` or `language:<name>`. `assembleReviewArtifact` stores the list and adds the file of each block to the sources.
- **An export carries its usages in the files that import it.** `generateCodeReferences(astGraphFiles, paths, exportedNamesByPath)` returns, beside the references of a file, its `exports`: for each name the file exports, the columns of the name it is declared under, the lines `findExportedLines` gives it, and every single-line use of it in another file of the cluster that `findDefinition` leads to those lines, through re-exports, with the whole text of the line. `buildCodegraph` gives the exported names of a file from the export table of its group (`exports` of the stored AST graph), and only for a changed file and a file that imports one, directly or through others, since only for those are all the importers traced: a file the change only imports gets no `exports`.
- **A name declared nowhere is assumed to be the language's.** `generateCodeReferences` in `code-references/` returns, beside the references of a file, its `languageReferences`: every reference on one line that `findDeclarationRange` finds no declaration for. Nothing checks the name against the language, so a name a tool provides without an import is among them. A reference that leads to a library carries `library`, the specifier and the imported name, from the `Definition` of `ast-graph/definition.ts`.
- **A hover definition takes its description from the context code blocks.** `buildCodeDefinitions` takes the list and the known link ids. A definition of code of the repository gets the description of the block on its lines (`definitionIdsOfBlock`), and a library definition the description of its name, so the definition id of a library holds the name too. A language name that has a description gets a definition of its own with no lines (`languageDefinitionIdOf`), and `codeLinesIn` puts a language reference on a line only when that definition exists.
- **The blast is the files that use a changed block.** `generateBlastFromBlocks({ group, filePaths, diffTypes })` in `blast-radius-diagram/from-blocks.ts` returns a `Blast` with one node per changed file of the segment and per file that holds a block using one of its changed blocks, directly or through other blocks (`listBlocksUsing` of `code-blocks/segments.ts`), each with its `diffType` and a `null` `impactType` and `impactReason` for a consumer to write, and one edge per use between two of them, from the file that uses to the file that is used. A file that imports a changed file and uses only what did not change is not in it. `blastRadiusDiagram` is `null` for an entry segment nothing outside the change uses, in a change of several segments. `generateBlastRadiusDiagram(importGraph)` draws an import graph as it is, and `buildCodegraph` uses it for a deleted file and the files that import it.
- **The import bound is the files the change uses.** `generateImportBound({ group, filePaths, diffTypes })` in `blast-radius-diagram/import-bound.ts` starts from the root block around every changed block of the segment, follows the `outerSymbols` of each root block and of every block inside it to the root blocks they name, and goes on from those. It returns one node per changed file of the segment and per file that holds a reached root block, and one edge per use between two files. `buildCodegraph` stores it as `importBound` of every blast it builds from blocks. It does not stop at a shared file, and it never decides whether a segment has a blast.
- **Which files the change reaches is one calculation, in `blast/assessment.ts`.** `listReachedPaths(blast)` gives the files the diff did not touch that import a changed file, directly or through other files, and stops at a file whose `impactType` is `unaffected`. `listUnassessedNodes` gives the reached files with no `impactType`, which is the work the backend hands the agent, and `listCarriedImports` gives the imports of a file that bring the change to it. The band and the backend's unwritten work both read reach from here, so they cannot disagree.
- **The blast board is columns of files, read from left to right.** `layoutBlast` in `blast/layout.ts` gives every file a column: one more than the furthest column of the files that import it, so every import points right and a file many files import is at the right of them all. An import that closes a loop is found by walking the imports and takes no part in the columns. The rows of a column are ordered by the mean row of the files each file is joined to, in a fixed number of sweeps from left to right and back, so imports cross little. A column is as wide as its widest label, and every column is centred on the height of the tallest. Nothing is random, so the same blast always gets the same board. Both views of a Blast Diagram use it.
- **A Blast Diagram band is a list of views.** `buildBlast` returns `views`: the export bound always, and the import bound when the blast has an `importBound`, each with its own label, description, summary, legend and board, laid out by the same `layoutBlast`. `defaultViewId` is the export bound, and the import bound when every file of the export bound is one of the segment's `changedPaths`. A file the diff did not touch is `used` in the import bound: plain, with a fixed `impactNote` and no `assessment`.
- **`buildBlast(segment, scope, fileAnchorIdByPath, context)` decides what a file shows.** A file of the change is marked `added`, `modified` or `deleted`. A file with `breaks` or `behaviour-changes` is marked with it and carries its `impactReason` as prose. Every other file is `plain`, and carries an `impactNote`: the fixed sentence for an unaffected, an unassessed or an unreached file. `markLabel` always says where the file stands, for the side panel. A file the change reaches, and a file that has an `impactType`, carries an `assessment`: its impact type, or `unassessed`, and its reason as Markdown, which is what the author's form starts from. A file of the change and an unreached file with no impact type have `null`. The band carries `assessmentForm`, the labels and the choices of that form.
- **A waypoint knows its kind and its nodes.** `generateWalkthroughFromBlocks` in `code-walkthrough/from-blocks.ts` makes one File Section per changed file of the segment and one waypoint per root block that holds a diff block, or per method when the change is inside a class. Imports, types or statements that follow each other are one waypoint. Each waypoint carries its line `range`, a `category` (`function`, `class`, `method`, `variable`, `import`, `type`, `statement`, or `file` for a file no language reads), the `journeyFlowId` and the `journeyNodeId` it belongs to, each `null` when the diagram has no node for it. These fields are declared in `code-walkthrough/` as `LinkedWaypoint`; the stored artifact in `packages/configurations` does not have them.
- **A changed declaration is read in parts.** `listWaypointSteps` in `code-walkthrough/steps.ts` gives the waypoint of a function, a class, a method or a variable one child per changed step, with the folding the rows of a journey node use (`journey-flow-diagram/step-folding.ts`) and rules of its own: a named function, an event, an effect and a callback hold steps as a body does, a run ends at a line that did not change, and inside markup only a `render-condition`, a `render-loop` and a `render-event` are steps. A lone child is left out for its own children. A function, hook, component, method, condition, loop, switch or case of fewer than six lines is read whole, with no children, and no two waypoints start on one line: a step on its parent's first line is left out for its children, and siblings that start on one line are joined. A child has the id of its parent and its place (`w3.2`), and the declaration of its parent and the name of its step (`renameUser › Condition :4`). [The steps of a waypoint](../../docs/vocabulary/code-walkthrough.md#the-steps-of-a-waypoint) has the rules.
- **A waypoint holds its blocks as aliases.** `generateWalkthroughFromBlocks` reads the linked group the journey of the segment is drawn from, and gives each waypoint `codeBlocks`: the block it stops at first, then the changed blocks inside it, in the order they are written, each the same object as in that group. `code-walkthrough/stored.ts` holds the form with ids in their place: `storeCodeWalkthrough` and `linkCodeWalkthrough` for a snapshot, and `storeWaypoint` and `storeFileSection` for what an agent reads.
- **The end-to-end cases live in another project.** `tools/playground-fixtures` holds the cases that run `buildBranchCodegraph` against whole repositories, and their snapshots. A change to what the codegraph produces changes those snapshots: run `nx test playground-fixtures`, and `nx run playground-fixtures:snapshot` after an intended change. A segment of the codegraph has a `title`, `null` until a case or a consumer writes it.
- **A rule has a fixture.** Every rule has a test in the `__tests__/` folder beside the code that implements it.

## Layout

```
src/import-graph/ the files a file imports and is imported by, traced through git-forge, with one module per language in languages/
src/shared/       the plumbing the folders share: a cache, grouping, records, running in order
src/ast-graph/    the syntax of one file: encapsulations, names, statements and syntax sites, with one reader per language in languages/<language>/
src/catalogue/    what a call into a library means, as data: one file per language and category of libraries, a fixture for every pattern, and matching/ that applies the patterns to a file
src/code-blocks/  the blocks of each file of a group, what each block uses, the block around each change, the chains, and the segments of a group
src/journey-flow-diagram/  the chains of a group in memory → the Journey Flow Diagram of a segment: its nodes, the nodes inside a node, its trigger labels and its edges, with its stored and its flat form
src/blast-radius-diagram/  the blocks that use the change of a segment → its Blast Diagram
src/code-walkthrough/      the diff blocks of a segment and its Journey Flow Diagram → its Code Walkthrough
src/code-references/       the files of a segment → where each name used in the viewed files is defined, and where each name they export is used
src/scaffold/     the segments of a codegraph, the diff and the files → the first review artifact: hunks, source lines, sources and segments
src/code/         source lines with their marks and references, code links, code definitions, highlighting a review, marked source for fixtures
src/prose/        Markdown prose → the prose shapes, and count labels
src/diagram/      what both diagrams share: the settings, levels through edges
src/journey/      Journey Flow Diagram: the names of its blocks, the code of a node, band
src/blast/        Blast Diagram: which files the change reaches, file labels, the layout in columns, the views of the band
src/walkthrough/  Code Walkthrough: waypoints, reviewed marks, file rows, band and controls
```

## Verify

- `nx build backend`, then start `node dist/apps/backend/main.js` once: the bundle is CJS and only the built server shows a package that does not load.
