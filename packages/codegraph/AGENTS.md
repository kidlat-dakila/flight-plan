# packages/codegraph

The engine that traces a change through the code, and the builders that turn a change into the parts of a review artifact and the bands the review page renders. Read [codegraph](../../docs/vocabulary/codegraph.md) before changing anything here.

## Rules

- **One entry.** `src/index.ts` is the only module another project imports, as `@flightplan/codegraph`. The package is consumed as source and has no build step. It is marked `"sideEffects": false`, so the backend's bundle keeps only what the backend calls.
- **The engine stands alone.** `src/core/` imports nothing from the builder folders, and lint rejects it (`import-x/no-restricted-paths` in `eslint.config.ts`).
- **Shapes come from `packages/configurations`.** The artifact's types and the band schemas are imported from `@flightplan/configurations`, never declared here. A builder's own input types live beside it: `ReviewViewContext` and `BlobLinker` in `review-view-context.ts`, `ReviewedMarks` in `walkthrough/reviewed-marks.ts`, `DiagramSettings` in `journey/filter.ts`.
- **A builder is a calculation.** Everything outside `src/core/` takes plain data and returns new data. What only the backend knows arrives as an argument: forge links as a `blobLinkOf` function, the lines a comment thread pins as a `pinnedLinesOf` function, highlighted code as `HighlightedSource`. A builder never reads a discussion, a store or a forge.
- **The core is calculations.** Everything in `src/core/` takes its inputs as arguments and returns new data. Three modules hold state or touch the outside, and nothing else may: `virtual-fs.ts` patches `node:fs` while dependency-cruiser reads a repository held in memory, `tracer/parse.ts` loads the grammar `.wasm` files from `tree-sitter/`, and `walk-stats.ts` counts the work a walk did.
- **The import graph reads through git-forge.** `src/import-graph/` answers who imports a file and what it imports, at one commit of a change. `createImportGraphContext({ gitAdapter, baseCommit, headCommit })` reads a change once, and `traceImportGraph(context, filePath)` traces one file through it in both directions. Every file, file list and search comes from the `GitAdapter`: `blobs`, `listFiles` and `searchFiles`. A changed file is traced at the head commit and a deleted file at the base commit. Each traced file carries `importedFilePaths`, the file every import specifier in it resolves to, whether that file is in the trace or not; `importsTo` lists only the files inside the trace. A Python import is named by `pythonSpecifierOf`: its module as written, then `:` and the name taken from it. `clusterImportGraphs(importGraphs)` joins the traces that share a file into one cluster, so a cluster is one connected part of one language.
- **An importer is searched for, then proven.** A language in `import-graph/languages/` gives the patterns an importer of a file would contain, `searchFiles` finds the candidates, and a candidate counts only when one of its imports resolves to the file. Dynamic `import()` calls are not imports.
- **A file of the AST graph is built once.** `src/ast-graph/languages/base.ts` holds `BaseASTGraphFile`, which every language extends. Its constructor takes a parsed tree and extracts the root encapsulations, the variables, the import variables and the references, and nothing changes them afterwards. It also takes `diffLines`, the line ranges the change touches in the file, and places them as `DiffLocation`s: a range of changed lines, the root encapsulation it lies in and the nearest encapsulation that holds it. A location belongs to one root encapsulation, so a range that spans several, such as the whole of a new file, is split into one location per root encapsulation and cut to its lines. Changed lines outside every root encapsulation have no location. A language implements the six `extract…` methods from the tree it is handed and never reads its own fields in them, because the base constructor runs them first: root encapsulations, file variables, import variables, references, export aliases and re-exports.
- **A group of the AST graph is one cluster of the import graph.** `ast-graph/ast-code-group-graph.ts` holds `ASTCodeGroupGraph`. Its constructor takes the files of a cluster with their source text and builds one file of the AST graph for each, with the class `languages/create-ast-graph-file.ts` picks from the file's extension; a file no language reads is left out. `readASTCodeGroupGraph({ gitAdapter, importGraph, diffLines })` is the only part that reads: it fetches the sources with one `blobs` call per commit. `traceDeepUsageFromAstGraphFile(astGraphFile, diffLocation)` returns the `DiagramNode` of the location's nearest encapsulation with its callers, and `traceAllDiffUsage()` returns one tree per changed encapsulation of the group.
- **A deep trace climbs through uses.** `ast-graph/trace-deep-usage.ts` asks the file of an encapsulation for the uses of its name, asks every file of the group for the uses of the names the file exports it by, and makes the nearest encapsulation of each use a caller, once, at its first use. It climbs from each caller the same way and never enters an encapsulation already on the path. A use outside every encapsulation gives no caller. The group never reads syntax: what a name is, who exports it and who uses it are answered by the files.
- **An encapsulation without a name of its own is traced through the one that holds it.** A method is not a variable, so its uses are the uses of its class, and its node is named `Class.method`. A root encapsulation is known to importers by its own name and by every export alias of that name: `default` for `export default function priceOf`, `price` for `export { priceOf as price }`.
- **A name is handed on only where it is exported.** A file hands an imported symbol on under the names it exports that import by, and under the names of its re-exports: `export { a as b } from`, `export * from`, which keeps every name but `default`, and `export * as ns from`. Python exports every name it imports. A namespace import counts as a use of a symbol only in a file that imports the symbol's own file, not one that reaches it through a re-export.
- **A change outside every encapsulation is a loose statement.** A top-level statement that no root encapsulation shares a line with (an import, a type, an interface, a bare call) is loose. `listLooseDiffLines()` gives the whole line range of every loose statement the diff touches, joined when they follow each other; when a file's changed lines are in no encapsulation and no statement at all, it gives the changed lines themselves, so a changed file is never without a place. `traceLooseDiffUsage()` traces each one to the uses of what it declares and names its node after those names, or `Lines 3–5` when it declares none. `traceLooseDeclarationUsage()` keeps only the ones that declare a name.
- **The new pipeline is `buildCodegraph`, and it lives in the entry.** `src/index.ts` holds it, beside the re-exports of the old builders the backend still calls. `buildBranchCodegraph({ gitAdapter, ref })` is where a caller starts: it takes a branch or a pull request, asks the adapter for its `baseSha` and `headSha`, and hands the two commits to `buildCodegraph`. It reads a change through git-forge once: it traces and clusters the import graph, reads the changed lines of each file from the patches of the comparison with `diffLinesOf` (`src/diff-lines.ts`), and builds one segment per cluster: `{ importGraph, astGraph, journeyFlowDiagram, blastRadiusDiagram, codeWalkthrough }`. A deleted file has no changed lines. Lines that were only removed count as a change on the line before them.
- **The new code takes nothing from `src/core/`.** `src/shared/` holds the plumbing the new folders share: `Memo` and `once` (`memo.ts`), `groupBy`, `recordOf` and `omit` (`record.ts`), `mapInSequence` (`sequence.ts`) and `firstOfEach`. The module resolvers of the import graph are in `import-graph/languages/`: `typescript-resolve.ts`, `python-module-roots.ts` and `python-resolve.ts`. They are copies of the modules in `src/core/`, which keeps its own until it is deleted.
- **The new generators import only `ast-graph/`, `import-graph/`, `shared/` and `@flightplan/configurations`.** `src/journey-flow-diagram/`, `src/blast-radius-diagram/`, `src/code-walkthrough/`, `buildCodegraph` in `src/index.ts` and `src/diff-lines.ts` replace `src/core/`, `src/scaffold/`, `src/journey/`, `src/blast/` and `src/walkthrough/`, and take nothing from them. The trees they read are `DiagramNode`s of `ast-graph/diagram-node.ts`.
- **Trees are merged into one graph before they are drawn.** `mergeDiagramNodes` in `ast-graph/usage-graph.ts` lists every declaration of the trees once, named by its file and its name, with one edge from each user to what it uses, and marks the root of every tree as changed. Two changes on one chain therefore share a diagram. Both diagram generators start from it.
- **A journey has an entry point per declaration nothing uses.** `generateJourneyFlowDiagram(segmentDiagramNodes)` returns one `JourneyFlow` for a segment, or `null` when nothing was traced. It adds an Entry Point Node, labelled with the declaration's name, and a `trigger` edge for every declaration no other uses. Every node has the category `logic` and every edge is `proven`, until the trace tells kinds and certainties apart.
- **A blast is never left out.** `generateBlastRadiusDiagram(segmentDiagramNodes)` always returns a `Blast`. A node's ring is its distance to the nearest change. `buildCodegraph` hands it the trees of the changed encapsulations and of the loose statements that declare a name, so a changed type is an Epicenter Node with its users around it; when both are empty it hands over every loose change, so a segment with any change has an Epicenter Node.
- **A waypoint knows its kind and its nodes.** `generateCodeWalkthrough` makes one File Section per file with changes and one waypoint per changed declaration: the function a change is in, the method when the function is inside a class, or a loose statement. Each waypoint carries its line `range`, a `category` read from the syntax tree (`function`, `class`, `method`, `variable`, `import`, `type` or `statement`), the `journeyFlowId` and `journeyNodeId` it belongs to and its `blastNodeId`, each `null` when the diagram has no node for it. These fields are declared in `code-walkthrough/` as `LinkedWaypoint`; the stored artifact in `packages/configurations` does not have them.
- **A language of the AST graph has its own folder.** `ast-graph/languages/typescript/` holds `TypescriptASTGraphFile` in `index.ts` and one module per extraction beside it: `encapsulations.ts`, `declarations.ts`, `imports.ts`, `references.ts` and `exports.ts`, with `scopes.ts`, `patterns.ts` and `syntax.ts` under them. The class reads trees of the `typescript` grammar. Each extraction asks the tree for the node types it reads with a tree-sitter query, through `nodesMatching` in `ast-graph/query-nodes.ts`, and does not visit the other nodes. `languages/nest-encapsulations.ts` nests the encapsulations a language found by what contains what.
- **JSX is TypeScript with elements.** `ast-graph/languages/jsx/` holds `JSXASTGraphFile`, which reads trees of the `tsx` grammar: `.tsx`, `.jsx` and plain JavaScript files. It reuses the TypeScript extractions and adds the element rules in `jsx/references.ts`: an element whose name starts with a capital, or that is a member such as `<Form.Field>`, is a use of that name, counted once at its opening tag. A lowercase element, a namespaced element and an attribute name are not uses. The specs in `typescript/__tests__/` run every TypeScript case against both classes through `SCRIPT_DIALECTS` in `languages/__tests__/script-files.ts`.
- **Python binds names, it does not declare them.** `ast-graph/languages/python/` holds `PythonASTGraphFile`. `bindings.ts` reads every place a name is bound (a `def`, a `class`, a parameter, an assignment target, a loop, `with`, `except`, `:=`, a `match` capture, a type parameter, an import) and keeps the first one in each scope as the declaration; a later binding of that name in that scope is a use. A scope is the body of a function or lambda, a comprehension, or the file. There is no block scope, `global` and `nonlocal` move a binding to the scope they name, and what a class body binds is neither a variable nor a use, because a method cannot see it. Every import of a name is kept when its first binding is an import, so `import shop.tax` and `import shop.pricing` both count.
- **A Python import of a name may be a module.** `from shop import pricing` has the imported name `*` when the file it resolved to is the module `pricing`, and `pricing` when the file is the package that defines it.
- **A Vue file is three languages.** `ast-graph/languages/vue/` holds `VueASTGraphFile`, which takes the tree of the whole file parsed with the `html` grammar (`tree-sitter-html`). `sfc.ts` finds the script blocks and the template in it. `script.ts` parses each script block with the TypeScript grammar its `lang` names and reads it with the TypeScript extractions. `template.ts` parses every expression of the template (an interpolation, a bound attribute, a handler, the two sides of a `v-for`, the properties of a slot) as a snippet of TypeScript. `snippet.ts` moves what a snippet found to its lines and columns in the file.
- **A Vue component is the default export.** A `<script setup>` block and the template are each a root encapsulation named `default`, and a file that does not export a default declares the variable `default`, so an importer's default import leads to them. The top level of a setup script is seen by the template, the top level of a script without setup is not. A `v-for` variable and a slot property are seen inside their element only. A capitalised tag, a tag with dashes and the object of a member tag are uses of the component's name, and `v-focus` is a use of `vFocus`.
- **A name is resolved once per space.** A declaration and a use each carry the spaces they live in, `value`, `type` or both, so `const Cart` and `type Cart` in one scope stay apart. A use belongs to the declaration of its name with the nearest scope in each of its spaces, and to every such declaration when several share that scope. A class, an enum, a namespace and an import are in both spaces.
- **An encapsulation is something a changed line can belong to.** At the root of a file that is a function, a class, a variable, an enum, a namespace or a default export. Below the root it is a function, a class, a method, or a variable, field or member of a declared object that holds a function or a class. Types, declarations marked `declare`, overload signatures and the members of an object handed to a call or to an element are not encapsulations. An object handed to `defineComponent` is the exception: its members are.
- **The new code parses through `ast-graph/parser.ts`.** It parses with the native `tree-sitter` package and the `tree-sitter-typescript`, `tree-sitter-python` and `tree-sitter-html` grammars, keeps one parser per grammar and the compiled queries, and is the only module of `ast-graph/` and `import-graph/` that holds state. Parsing is synchronous and a tree is freed by the garbage collector. Neither folder parses through `core/tracer/parse.ts`, which keeps `web-tree-sitter` and the `.wasm` files in `tree-sitter/` for the old engine.
- **The import graph reads git in batches.** A trace asks for the importers of every file of a level in one `searchFiles` call, and reads the files of a level in one `blobs` call through `RepositorySnapshot.preload`. Code in `import-graph/` never searches or reads once per file in a loop.
- **A tree is walked with a cursor.** `ast-graph/walk-tree.ts` holds `collectFromTree` and `collectFromNode`, which visit nodes through a tree-sitter `TreeCursor`. Code in `ast-graph/` walks with them, never with a recursive read of `children`.
- **Syntax nodes are read, never cast.** A TypeScript or JavaScript node is read through `childAt`, `childrenAt`, `slotsAt` and `textAt` in `tracer/typescript/node.ts`. A missing child is `null` and the caller handles it.
- **An analysis returns what it found.** The value-flow analysers return findings: an invocation, an escape, or a task to analyse next. Only `traceValueFlow` folds them into a result, which keeps the order of the output independent of the order the files were read in.
- **Shared plumbing has one home.** A cache is a `Memo` (`memo.ts`), a group is `groupBy` (`group-by.ts`), a loop that must run in order is `mapInSequence`, `someInSequence`, `findInSequence` or `reduceInSequence` (`sequence.ts`), and a loop that runs until a state is reached is `iterateUntil` (`iterate.ts`).
- **One lint override.** `eslint.config.ts` turns off `n/no-sync` and `n/prefer-promises/fs` for `src/core/__tests__/virtual-fs.spec.ts`, because that spec tests the synchronous file system calls the mount answers. No other file may call a synchronous or callback `fs` function.
- **The playground has its own guide.** Read [docs/playground.md](docs/playground.md) before adding a case or a kind: it says how a case is laid out, what is mocked and how a diff is written.
- **A case is a repository and a diff.** `playground/<language or repository kind>/` holds one test file, `<kind>.integration.test.ts`, the repository it reads in `repo/`, and one committed snapshot per test in `snapshots/<test name>.snapshot.json`. `repo/` is the repository before the change. A test calls `setupTest({ repoPath, diffs })`, where `diffs` are unified diff texts that each open a file with a `diff --git` line, so one repository serves many changes. It then opens the repository with `assembleGitAdapter`, hands the adapter and the branch `CASE_BRANCH` to `buildBranchCodegraph`, and gives the whole result to `expectCaseSnapshot`, which writes a `Map` as the record of its entries.
- **The cases read through a mocked `@flightplan/git-forge`.** `test-setup/mock-git-forge.ts` is a Vitest setup file that replaces `assembleGitAdapter`, `readRemote` and `repoName`, and keeps the rest of the package real. `setupTest` makes them answer from the case: the base commit is the files in `repo/`, the head commit is those files with the diffs applied, and the diff of the change is the diffs. Before `setupTest` is called they reject, and they are reset after every test.
- **`repo/` is data.** ESLint, TypeScript, Vitest and Nx all skip `playground/*/repo/`, so a case repository may hold code that would not lint, compile or resolve. The package's source never imports `playground/` or `test-setup/`, and lint rejects it.
- **A rule has a fixture.** Every rule in the vocabulary's core logic has a test in the `__tests__/` folder beside the code that implements it. `demo.output.json` is the recorded output of `demo.ts`, checked as a file snapshot.

## Layout

```
src/core/         the engine
src/import-graph/ the files a file imports and is imported by, traced through git-forge, with one module per language in languages/
src/shared/       the plumbing the new folders share: a cache, grouping, records, running in order
src/ast-graph/    the encapsulations, variables and uses inside one file, with one class per language in languages/<language>/
src/journey-flow-diagram/  the trees of a segment → its Journey Flow Diagram
src/blast-radius-diagram/  the trees of a segment → its Blast Diagram
src/code-walkthrough/      the files of a segment and its two diagrams → its Code Walkthrough
src/scaffold/     a change's diff and files → the first review artifact: hunks, declarations, File Sections and waypoints, source lines
src/code/         source lines, code links, highlighting a review, marked source for fixtures
src/prose/        Markdown prose → the prose shapes, and count labels
src/diagram/      what both diagrams share: the configuration, the legend, levels through edges
src/journey/      Journey Flow Diagram: filter, layout, band
src/blast/        Blast Diagram: filter, shields, layout, band
src/walkthrough/  Code Walkthrough: waypoints, reviewed marks, file rows, band and controls
playground/<kind>/  <kind>.integration.test.ts, repo/ and snapshots/ for one language or repository kind
test-setup/       setupTest, the git-forge mock, applying diffs to a repository, the case snapshot
```

## Verify

- `nx run-many -t eslint:lint typecheck test -p configurations git-forge codegraph backend`
- `nx test codegraph` checks every case against its committed snapshot. `nx run codegraph:snapshot` rewrites the snapshots after an intended change in behaviour.
- `nx build backend`, then start `node dist/apps/backend/main.js` once: the bundle is CJS and only the built server shows a package that does not load.
