# packages/codegraph

The pipeline that traces a change through the code, and the builders that turn a change into the parts of a review artifact and the bands the review page renders. Read [codegraph](../../docs/vocabulary/codegraph.md) before changing anything here.

## Rules

- **One entry.** `src/index.ts` is the only module another project imports, as `@flightplan/codegraph`. The package is consumed as source and has no build step. It is marked `"sideEffects": false`, so the backend's bundle keeps only what the backend calls.
- **Shapes come from `packages/configurations`.** The artifact's types and the band schemas are imported from `@flightplan/configurations`, never declared here. A builder's own input types live beside it: `ReviewViewContext` and `BlobLinker` in `review-view-context.ts`, `ReviewedMarks` in `walkthrough/reviewed-marks.ts`, `DiagramSettings` in `diagram/settings.ts`.
- **A builder is a calculation.** Every builder takes plain data and returns new data. What only the backend knows arrives as an argument: forge links as a `blobLinkOf` function, the lines a comment thread pins as a `pinnedLinesOf` function, highlighted code as `HighlightedSource`. A builder never reads a discussion, a store or a forge.
- **The pipeline is `buildCodegraph`, and it lives in the entry.** `src/index.ts` holds it, beside the re-exports of the builders the backend calls. `buildBranchCodegraph({ gitAdapter, ref })` is where a caller starts: it takes a branch or a pull request, asks the adapter for its `baseSha` and `headSha`, and hands the two commits to `buildCodegraph`. It reads a change through git-forge once: it traces and clusters the import graph, builds the groups of code blocks with `readCodeGroups`, which also reads the manifests of the repository and keeps the syntax of each file beside its group, cuts each group with `cutSegments`, and builds one segment per cut: `{ kind, importGraph, journeyFlowDiagram, blastRadiusDiagram, codeWalkthrough, codeReferences }`. A changed file no cluster holds, such as a migration, is a group and a segment of its own. A deleted file has no blocks: it is with the first segment of its cluster, or alone in a segment when its cluster has no group.
- **A requested review is the codegraph of its branch, assembled.** `buildBranchReviewArtifact({ gitAdapter, ref, title, newId })` in `src/index.ts` runs the pipeline once and returns a drafting `ReviewArtifact` with the commit the branch started from. It reads the hunks of each file from the patches the import graph context already holds (`hunkOfPatch`), reads the head text of every changed file and of every file a journey or a code reference shows with one `blobs` call, and hands both to `assembleReviewArtifact` in `scaffold/review-artifact.ts`. That calculation maps a segment of the codegraph to a segment of the artifact, drops the fields of a `LinkedWaypoint` the stored artifact does not have, and builds each source file with the declaration of every waypoint on its lines. `tools/playground-fixtures` assembles a snapshot through the same function, so a fixture and a requested review cannot differ in shape. It is the one function of the entry that reads `src/scaffold/`; `buildCodegraph` still takes nothing from it.
- **Shared plumbing has one home.** `src/shared/` holds what the folders share: `Memo` and `once` (`memo.ts`), `groupBy` (`group-by.ts`), `recordOf` and `omit` (`record.ts`), `mapInSequence` (`sequence.ts`) and `firstOfEach` (`first-of-each.ts`). The module resolvers of the import graph are in `import-graph/languages/`: `typescript-resolve.ts`, `python-module-roots.ts` and `python-resolve.ts`.
- **Every cluster is drawn from code blocks.** TypeScript, JavaScript, JSX, Vue and Python each have a language in `code-blocks/languages/`, and a file none of them reads is one `file` block. A file is parsed once: the language that reads its blocks also reads its syntax, and `buildCodegraph` builds the files of the AST graph of a cluster from it with `listASTGraphFiles`, which `generateCodeReferences` reads the names from. `buildCodegraph` links each group once with `linkCodeGroupGraph`, and `generateJourneyFlowDiagram` draws every segment of a group from that one group in memory, so the diagrams of two segments hold the same blocks.
- **The generators import only `ast-graph/`, `code-blocks/`, `import-graph/`, `shared/` and `@flightplan/configurations`.** `src/journey-flow-diagram/`, `src/blast-radius-diagram/`, `src/code-walkthrough/`, `buildCodegraph` in `src/index.ts` and `src/diff-lines.ts` take nothing from `src/scaffold/`, `src/journey/`, `src/blast/` and `src/walkthrough/`.
- **A line carries its marks and the definitions it leads to.** `codeLinesIn` in `code/lines.ts` takes `LineDecorations`: the marks of a view, the line spans shown with it and the ids of the known definitions. A line gets the marks on it and the references of its source file in columns that start at one and end on the last character. A reference is left out when its definition is not known or lies on the lines shown. `buildCodeDefinitions` in `code/definitions.ts` builds one definition per reference target that has a source, keyed by `definitionIdOf`, with a note for a library, and draws its lines with no references. The Code Walkthrough passes the lines of every row it shows as the lines shown.
- **The blast is the files that use a changed block.** `generateBlastFromBlocks({ group, filePaths, diffTypes })` in `blast-radius-diagram/from-blocks.ts` returns a `Blast` with one node per changed file of the segment and per file that holds a block using one of its changed blocks, directly or through other blocks (`listBlocksUsing` of `code-blocks/segments.ts`), each with its `diffType` and a `null` `impactType` and `impactReason` for a consumer to write, and one edge per use between two of them, from the file that uses to the file that is used. A file that imports a changed file and uses only what did not change is not in it. `blastRadiusDiagram` is `null` for an entry segment nothing outside the change uses, in a change of several segments. `generateBlastRadiusDiagram(importGraph)` draws an import graph as it is, and `buildCodegraph` uses it for a deleted file and the files that import it.
- **Which files the change reaches is one calculation, in `blast/assessment.ts`.** `listReachedPaths(blast)` gives the files the diff did not touch that import a changed file, directly or through other files, and stops at a file whose `impactType` is `unaffected`. `listUnassessedNodes` gives the reached files with no `impactType`, which is the work the backend hands the agent, and `listCarriedImports` gives the imports of a file that bring the change to it. The band and the backend's unwritten work both read reach from here, so they cannot disagree.
- **The change is at the centre of the blast board.** `layoutBlast` in `blast/layout.ts` gives every file a ring: the files of the change first, a file further in the deeper it is among the changed files (in `a.ts → b.ts → c.ts`, `c.ts` is innermost), then every other file by the number of imports between it and the change. A ring is at least wide enough for its files. Files are pushed apart, pulled to their ring and, weakly, toward the files they are joined to, for a fixed number of steps from fixed starting points, so the same blast always gets the same board. The board is symmetric around the centre.
- **`buildBlast(segment, scope, fileAnchorIdByPath, context)` decides what a file shows.** A file of the change is marked `added`, `modified` or `deleted`. A file with `breaks` or `behaviour-changes` is marked with it and carries its `impactReason` as prose. Every other file is `plain`, and carries an `impactNote`: the fixed sentence for an unaffected, an unassessed or an unreached file. `markLabel` always says where the file stands, for the side panel.
- **A waypoint knows its kind and its nodes.** `generateWalkthroughFromBlocks` in `code-walkthrough/from-blocks.ts` makes one File Section per changed file of the segment and one waypoint per root block that holds a diff block, or per method when the change is inside a class. Imports, types or statements that follow each other are one waypoint. Each waypoint carries its line `range`, a `category` (`function`, `class`, `method`, `variable`, `import`, `type`, `statement`, or `file` for a file no language reads), the `journeyFlowId` and the `journeyNodeId` it belongs to, each `null` when the diagram has no node for it. These fields are declared in `code-walkthrough/` as `LinkedWaypoint`; the stored artifact in `packages/configurations` does not have them.
- **The end-to-end cases live in another project.** `tools/playground-fixtures` holds the cases that run `buildBranchCodegraph` against whole repositories, and their snapshots. A change to what the codegraph produces changes those snapshots: run `nx test playground-fixtures`, and `nx run playground-fixtures:snapshot` after an intended change. A segment of the codegraph has a `title`, `null` until a case or a consumer writes it.
- **A rule has a fixture.** Every rule has a test in the `__tests__/` folder beside the code that implements it.

## Layout

```
src/import-graph/ the files a file imports and is imported by, traced through git-forge, with one module per language in languages/
src/shared/       the plumbing the folders share: a cache, grouping, records, running in order
src/ast-graph/    the syntax of one file: encapsulations, names, statements and syntax sites, with one reader per language in languages/<language>/
src/catalogue/    what a call into a library means, as data: one file per language and category of libraries, a fixture for every pattern, and matching/ that applies the patterns to a file
src/code-blocks/  the blocks of each file of a group, what each block uses, the block around each change, the chains, and the segments of a group
src/journey-flow-diagram/  the chains of a group in memory → the Journey Flow Diagram of a segment: its nodes, the nodes inside a node, its trigger labels and its edges, with its stored and its flat form
src/blast-radius-diagram/  the blocks that use the change of a segment → its Blast Diagram
src/code-walkthrough/      the diff blocks of a segment and its Journey Flow Diagram → its Code Walkthrough
src/code-references/       the files of a segment → where each name used in the viewed files is defined
src/scaffold/     the segments of a codegraph, the diff and the files → the first review artifact: hunks, source lines, sources and segments
src/code/         source lines with their marks and references, code links, code definitions, highlighting a review, marked source for fixtures
src/prose/        Markdown prose → the prose shapes, and count labels
src/diagram/      what both diagrams share: the settings, levels through edges
src/journey/      Journey Flow Diagram: the names of its blocks, the code of a node, band
src/blast/        Blast Diagram: which files the change reaches, file labels, the layout around the change, band
src/walkthrough/  Code Walkthrough: waypoints, reviewed marks, file rows, band and controls
```

- `nx build backend`, then start `node dist/apps/backend/main.js` once: the bundle is CJS and only the built server shows a package that does not load.
