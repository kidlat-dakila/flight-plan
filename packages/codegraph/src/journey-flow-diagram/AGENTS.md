# packages/codegraph/src/journey-flow-diagram

The trace from the files of a segment to its Journey Flow Diagram. Read [Journey Flow Diagram](../../../../docs/vocabulary/journey-flow-diagram.md) before changing anything here, then [JavaScript and JSX](../../../../docs/vocabulary/codegraph/languages/jsx.md#journey-flow-diagram) and [Vue](../../../../docs/vocabulary/codegraph/languages/vue.md#journey-flow-diagram) for what a component adds. The rules of [packages/codegraph/AGENTS.md](../../AGENTS.md) hold here too.

## Rules

- **A journey is traced from the files, not from the trees.** `generateJourneyFlowDiagram(astGraphFiles)` returns one `JourneyFlow` for a segment, or `null` when no code that runs changed. `journey-flow-diagram/trace.ts` starts at every changed encapsulation and climbs through its uses to what triggers it. A node is a root encapsulation: a change inside a nested function or a method belongs to the node of the root that holds it. Nothing is traced downward, so a path ends at its last change. A use in an export list, an import or a type is not a use.
- **One trace serves every language, and JSX differs only through its syntax sites.** Nothing in `journey-flow-diagram/` asks whether a group holds JSX. A JSX file gives `attribute`, `element`, `markup` and `page` sites and `markup` statements, and those are what produce handler nodes, context readers, route visits and traced lines through markup. A file without them is traced by its calls alone.
- **A use has a role, and the role decides the climb.** `journey-flow-diagram/usage-role.ts` reads the syntax sites around a use, the narrowest first: a call or a render makes the encapsulation that holds it the next node; a handler on a built-in element ends the path at a user action; a prop on a component is followed into that component (`resolve-props.ts`), to where the prop is run, whether the component reads it from its parameter, takes it apart in its body (`const { onSave } = props`) or keeps it in a variable of its own; a page in a route table (`element` or `component` beside a `path`, a `<Route>`, a file route) ends at the visit of that route, named with its whole path; a route registration ends at an API call, a subscription (`on`, `once`, `addListener`, `subscribe`) at an event bus, a function handed to `addEventListener` at a user action named after its event and the object it listens on; a `Provider` value is followed to the components that read the context (see below); a function handed to a call whose result is kept takes its entry point from where that result is used. A use at the top level of a file ends the path at the entry point its syntax names.
- **A change inside a member is traced through the uses that take that member.** A changed action of a store, or any member without a declaration of its own, is followed only through the uses of its holder that name it on the same line, such as `useCartStore((state) => state.addItem)`, and then through what keeps the result. When no use names the member, every use of the holder counts. Every nested encapsulation a changed range touches is a starting point, so a hunk that covers a handler and the lines around it still starts at the handler.
- **A context is followed to the components that read it.** `journey-flow-diagram/context-readers.ts` finds the uses of the context handed to `useContext` or `use`. A reader that keeps the whole value is followed through that value; a reader that takes the value apart is followed only through the member with the name of what was provided, and through every member when the provided value reached the `Provider` through a call such as `useMemo`. From there the result is traced like the result of a hook: called from a handler it ends at a user action, read in the render body at a page visit. The reader has a `value` edge to the encapsulation that renders the `Provider`. When no reader takes it, the path ends at the `boundary` entry `Reached through a context`.
- **An entry point carries where the trace ended.** An `EntryFact` has an `end`: the file and the range of the handler attribute, the listener, the route, the page site or the last use, with the event, the element and, for a component imported from outside the repository, the import specifier (`findExternalImportSpecifier`). `generateJourneyFlowDiagram` stores it as the node's `traceEnd`, with the line and its source. The entry point of changed bare statements has none.
- **A user action leads to a node for its handler, not to the component.** `generateJourneyFlowDiagram` gives every entry point with an `actedAt` (a handler attribute, or a listener inside an encapsulation) a Code Node of its own. Its ranges are the attribute or listener and the functions declared in the component that run at it; an edge whose use lies in those ranges leaves from the handler node, and the trigger edge arrives at it. An edge to the result of a hook is one fact per use of the result (`keptAt` is the call that keeps it), so a result used in a handler leaves from the handler node and a result read in the body from the component. Where the handler runs a prop, the node moves to the component that hands the handler over (`handedAt` on the edge, set where the trace follows a prop): the entry point then leads to `CartPage.handleCheckout`, and the trigger edge's `through` lists `Button.onClick` and the props between. A handler node is named `<component>.<handler or attribute>`, has the id of its component with the event and the line, is changed when a changed line overlaps its ranges, and its `tracedLines` are the element acted on and the handler. A component is a changed node only when a changed line lies outside every handler range that spans more than one line.
- **An entry point with no node under it is left out.** `generateJourneyFlowDiagram` keeps an Entry Point Node only when its trigger edge arrives at a node that is drawn. An entry point with one Code Node under it and nothing else is a path and is drawn.
- **A component is the only `ui` node and a handler node the only `event` node.** `toDeclarationNode` in `journey-flow-diagram/index.ts` gives `ui` to a root encapsulation that `isComponent` of `entry-points.ts` accepts (a capitalised name or a default export, with markup inside) and `logic` to every other encapsulation: a function, the top level of a file, a constant that holds markup. `toActionDeclarationNode` gives `event` to every handler node. The two are `GENERATED_NODE_CATEGORIES` in `packages/configurations`: the backend's `amend-journey.ts` refuses an agent's edit that writes or replaces one, and the playground's `written-parts.ts` keeps the generated one over a snapshot's.
- **A node says how it stands to the diff with `changeType`.** A Code Node is `diff` when a changed line is on it and `related` otherwise, since an unchanged node is only drawn on the way to a change; it is never `none`. `isChanged` is left on a traced line only.
- **A value read in markup is absorbed into the component's data.** In `generateJourneyFlowDiagram`, an edge is a data read (`isDataRead`) when it leaves a component, its use is one of `listDataReads` of that component, and it arrives at an encapsulation of the kind `variable` or is the read of a hook's result (`keptAt` is set). A site at least one data read arrives at, that every other edge into is the read of a hook's result by a component (`isAbsorbable`), that no entry point leads to and that no edge leaves from is in `listAbsorbedSiteIds`: it gets no node and no edge. A handler node that is unchanged and has no edge left is dropped with its entry point (`leadingActions`). The read is `related` in the component's `data` when the site is changed, and a diagram whose only change is absorbed is headed by the components that read it. `journey/filter.ts` treats such a component as a head.
- **A `ui` node lists its events and its data.** `journey-flow-diagram/traced-names.ts` reads them from the syntax sites and the value references inside the component: `listTracedEvents` gives one entry per callback attribute (an `on…` name, a function written in place, or a function declared in the component) and per `addEventListener` argument, and `listTracedData` one per variable read inside a `markup` site, without element names, plain callees, variables declared inside the markup and what lies in a callback attribute. An entry is `{ name, changeType, reference }`, where `reference` is a line tuple and `changeType` is `diff` when a changed line is on the entry, `related` when one is on the function declared in the component that an event hands over or on the declaration statement of a variable inside the component, and `none` otherwise. The link never leaves the component. An entry of `events` also carries `nodeId`, the id of the drawn handler node whose ranges hold the attribute or the listener, or `null`. Every other node has both lists empty.
- **A component with several returns lists them.** `journey-flow-diagram/component-returns.ts` reads the `return` statements of a component's own body from its statements: it descends through conditionals, loops and `try` blocks, and never into a declaration, an expression or markup, so a `return` of a nested function or a callback is not one. With two or more, `listComponentReturns` gives one `ComponentReturn` each, in source order: an id (`<node id>#return@<line>`), the `statement` (the first line up to and including `return`), its lines, `diff` or `none`, the traced lines up to the end of the return, and `renderedNodeIds`, the nodes of the render edges whose use lies in the return, in reading order. A component with one return, and every node that is not a component, has `returns` empty.
- **An Entry Point Node says what triggers the path.** `journey-flow-diagram/entry-points.ts` holds the triggers and their labels: `page-visit`, `user-action`, `api-call`, `command`, `boundary`, `app-start` and `unused`. Every path has one. A changed handler written in place on a built-in element gives its handler node a user action of its own.
- **An unchanged encapsulation that only forwards is a step on the edge.** A component that passes a prop on, and a function whose whole body is one call, are not nodes: their names are the edge's `through`. A changed encapsulation is always a node, and so is one the path would otherwise end on.
- **A node carries its traced lines, and an edge carries none.** `journey-flow-diagram/traced-lines.ts` lists the source lines a debugger would step through in a root encapsulation: a statement on the way with every line it spans, a branch, a loop or an inner function the path does not go into by its first lines only, and nothing after the target. In a JSX file an element is a statement of the type `markup`, nested under the element that holds it, so the lines step into the elements above a hand-over and stop at it. A node's `tracedLines` run to its changed lines, or to where the path leaves it when the diff did not touch it. They are how the inside of a node is shown without more nodes: a branch or a `.map` of a component is lines of that component. Changed bare statements at the top level of a file are one node named `top level`, whose traced lines are those statements. A changed import or type gives no node.
- **A node says which code is read beside it.** `journey-flow-diagram/code-views.ts` gives every Code Node and every return of a component its `codeViews`: a `kind`, a `path`, the `lines` as line spans, the `marks` as single-line column spans in reading order and an `entryCount`. A node that is not a component has one `declaration` view of its whole root encapsulation, and the top level of a file one of its changed statements. A component has a `data` view per file a value it reads in markup is declared in, with a mark on the declared name; one `event` view of every callback attribute and listener, each from the line its element starts on to the end of the attribute, with the functions the component declares for it and a mark on the attribute; and one `render` view of its `return` statements, or of the whole component when it has none. A return has the `data` and the `event` views of what lies on its lines, then its own `render` view. A handler node has one `event` view of its attribute and the handlers run at it. `journey-flow-diagram/return-statements.ts` lists the `return` statements both the returns and the views read.
