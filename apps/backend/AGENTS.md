# apps/backend

The Fastify 5 server and imperative shell: HTTP, tRPC transport, MCP transport and I/O adapters (git, file system, forges). Read [architecture](../../docs/agents/architecture.md), [functional programming](../../docs/agents/functional-programming.md) and [fastify](../../docs/agents/fastify.md) before changing anything here.

## Rules

- **All logic lives on the backend side**, and the frontend only renders. Responses are display-ready: already filtered, sorted, grouped and formatted.
- **Procedures hold the logic. Transports only validate and invoke.** Every piece of backend logic is a procedure in `procedures/<procedure>/`, whether tRPC, MCP or a raw route calls it, and even while only one transport calls it today — this is what keeps the transports from drifting apart or duplicating a check. `server/trpc/routes/<procedure>/`, `server/mcp/tools/<tool>/` and `server/api/routes/<endpoint>/` are wrappers: they validate the request with the procedure's zod schema, call the procedure, and translate its result into that transport's shape (an HTTP status, a `TRPCError`, an MCP error content block). A wrapper earns more than that only when the transport truly needs it — reshaping a response, fanning out to more than one procedure, mapping a procedure's result to that transport's error format — never business logic.
- **A procedure is a plain async function**, `(input, context) => result`, exported from `procedures/<procedure>/index.ts`. It returns data, including failure as a value (a discriminated union, a nullable result); it does not throw transport errors. The wrapper that called it decides what a given result means for its transport.
- `procedures/<procedure>/utils/` holds that procedure's own schemas and pure calculations, with `__tests__/` next to each. Logic more than one procedure needs moves to a `<feature>/` folder at `src/` root instead (domain types, store interfaces, shared calculations), never duplicated into two procedures' `utils/`.
- `main.ts` is the only file that reads `process.env` and calls `listen`. `buildServer()` builds the instance for both production and tests.
- Register plugins explicitly in `buildServer`. No `@fastify/autoload`, because it breaks in the esbuild bundle.
- **Procedures reach I/O through `ProcedureContext`.** `procedures/context.ts` names each piece of I/O as an interface, such as `RepositoryStore`, the clock and the notice about the data. `createMockProcedureContext` fills them with in-memory stores seeded from a feature's `mock-<things>.ts`. Mocked data lives behind those interfaces, never in a procedure body, so real adapters replace the stores and the procedures stay as they are. `createLocalProcedureContext` is the context `main.ts` runs with: it starts from the mock context and swaps in the real adapters from `utils/` that exist so far (the setup stored in the data directory, agent detection, agent installing, the agents' model lists, the repository folder search, and the repository store). The models and efforts an agent offers come from the agent: `utils/agent-model-lister/` asks its command line program once per run and `offerModels` in `procedures/get-setup/utils/agent-models.ts` turns the answer into the offers the setup page, the review start form and their validation all share, so there is no model list to keep in step. `LiveRepositoryStore` lists the repositories the setup registered, reads each one through `RepositoryInspector` (the forge adapters in `utils/git-adapter/` and local git), and keeps the new-target marks in `targets.json`. The author search on a forge goes through `utils/author-lookup/`, which opens the repository's adapter with `utils/repository-adapter-opener/` (the same choice of forge as the inspector) and calls `searchPeople`. The review store is `utils/review-file-store/`: a review artifact is a `.flightplan` file under `reviews/<repository>/` in the data directory, and every other part of the store (reviewed marks, comments, publications, chat) is still the sample store behind it, which also serves the sample artifacts. The sample data notice is left out for a review target the sample store does not hold. A review request (`review.request`) opens the repository's git adapter through `context.openRepository` (the same opener the inspector and the author lookup use, a refusing one in the mock context), builds the whole review artifact of the branch with `buildBranchReviewArtifact` from `@flightplan/codegraph` (`procedures/request-review/utils/build-artifact.ts`, which turns a `GitAdapterError` into an `unavailable` result), and saves it with the request. Only then does it hand over the prompt or start the chosen agent through `deliverToAgent`, which runs the model and the effort the request names, so the page opens the artifact while the agent writes and the agent never builds structure. The request returns once the agent's process is launched, not when the agent is done. A rebuild (`review.rebuild`, with the form of its dialog from `review.rebuildForm`) takes the same choices and a mode: it pulls the branch through `context.pullBranch` (`utils/branch-puller/`, a no-op in the mock context) and returns `unavailable` with the reason when the pull fails, builds the artifact the same way, and in `update` mode carries the written parts of unchanged code over with `carryWriting` (`procedures/rebuild-review/utils/carry-writing.ts`), a calculation over the two artifacts; `regenerate`, or an update with another configuration, carries nothing. `review.delete` removes the stored artifact through `ReviewStore.deleteScaffold`. `ChangeReader` (`utils/git-change-reader/`) reads the head commit and the changed paths of a live review target for the page.
- **An agent fills a review artifact through six MCP tools, each a wrapper over one procedure**: `get-instructions`, `read` (`read-artifact`), `nodes` (`read-nodes`), `update-document`, `update-nodes` and `complete` (`complete-artifact`). Every one names the review target by `repositoryName` and `targetId`, opens it with `openArtifact` (which rejects an unknown target and a target with no artifact, and counts the call as agent activity), and reads the configuration from the artifact's request, never from its input. The tools change words and never structure: no input schema has a field for a path, a declaration, a child or an edge. A write goes through `reviewStore.amendArtifact`, which applies amendments to one artifact one after the other, so tool calls an agent makes in parallel cannot lose each other's writes. An amendment is a pure function that returns the new artifact or a refusal, a batch is all or nothing, every `code:` link in written prose must resolve in the artifact's `sources`, and any write puts the artifact back to `drafting`. The `blast` list of `update-nodes` writes an `impactType` and an `impactReason` on a Blast Diagram file, named by its path: `amendBlast` refuses one on a file of the change, a `breaks` or a `behaviour-changes` with no reason, and a reason on an `unaffected` file, and clears the reason of a file that becomes `unaffected`. A file the change reaches with no `impactType` is `impact` work, which `listUnassessedNodes` of `packages/codegraph` decides. What is still unwritten is one list, `unwrittenWork` in `procedures/read-artifact/utils/`, which `nodes`, `read` and `complete` all use, so they cannot disagree about what is left.
- **The review page's bands are built in `packages/codegraph`, from shapes in `packages/configurations`.** `procedures/get-review/` calls `buildJourney`, `buildBlast`, `prepareWalkthrough` and `buildWalkthrough`, and hands them what only the backend knows: a `blobLinkOf` function made from the repository's forge (`utils/forge-links.ts`), and the lines its comment threads pin. `buildBlast` also gets the anchor of each File Section by path, taken from the walkthrough band built just before it, so a file on the Blast Diagram can link to its File Section. `attachThreads` in `utils/discussion.ts` then adds each file's threads, which is why `utils/schemas.ts` extends the File Section and Code Walkthrough schemas with `threads`. `utils/schemas.ts` holds the page's own schemas only (header, rail, notices, Context Section, conversation, sharing, start form) and composes the band schemas into `reviewPageSchema`. `utils/stored-review.ts` wraps `reviewArtifactSchema` with the request and the base commit. Do not add a diagram, walkthrough or scaffold calculation here: it belongs in the package.
- **An author edits the Journey Flow Diagram through `review.editJourney`** (`procedures/edit-journey/`), one edit per call: adding, clearing, describing and removing the diagram, moving cards, drawing and removing a line, deleting a card, adding a card and changing a card. An `add-card` can carry a `lineEnd`, for a line the author dropped on the empty board: the card is then saved with that line and at that position, in the same edit. `planDiagramEdit` in its `utils/` is the calculation, over the artifact and, for a new card, the text of its file, which the procedure reads first with `readFileText` of `procedures/get-file-code/utils/file-text.ts`. Like `review.editContext` and `review.editSegments` it leaves the status of the artifact as it is. `review.cardBlocks` (`procedures/list-card-blocks/`) lists the root blocks of a file for the Add Card dialog, and `review.cardForm` (`procedures/get-card-form/`) returns what the Modify Card dialog shows: the label, the description, the rows, the kinds a row can be with a label for each, and the waypoints of the file. The cards themselves are built in `packages/codegraph` (`journey-flow-diagram/cards.ts`).
- **An author edits the impact of a Blast Diagram file through `review.editBlast`** (`procedures/edit-blast/`), one file per call, named by its path: an impact type, or `unassessed` to take the assessment back, and the reason as Markdown. `planBlastEdit` in its `utils/` is the calculation. It writes the file in every Blast Diagram that holds it, as the agent's `update-nodes` does, rejects a file of the change, a `breaks` or a `behaviour-changes` with no reason and a code link to code the artifact does not hold, and drops the reason of a file that becomes `unaffected` or unassessed. It leaves the status of the artifact as it is. Nothing else of a Blast Diagram has a route.
- **An author edits the Code Walkthrough of a segment through `review.editWalkthrough`** (`procedures/edit-walkthrough/`), one edit per call: `move-file` moves a File Section one place up or down, `remove-file` takes a File Section out of the walkthrough and leaves the file among the segment's files, `change-waypoint` writes a waypoint's title, reading and Needs Attention reason, with `null` for no mark, and `remove-waypoint` removes a waypoint and keeps the waypoints inside it in its place. `planWalkthroughEdit` in its `utils/` is the calculation. It rejects a waypoint with no title and a code link to code the artifact does not hold. A Needs Attention mark may have no reason: it is then stored as an empty text, which is still a mark. It leaves the status of the artifact as it is, and the findings of a waypoint have no route. `review.get` takes `isAuthoring` for the author's page: the page is then built with no reviewed marks, so nothing on it is reviewed or hidden as reviewed.
- **The progress of a drafting review is decided here, in `procedures/get-review/utils/build-progress.ts`.** `buildProgress` counts the written parts with `tallyNodes` of `procedures/read-artifact/utils/unwritten-work.ts`, the same tally the MCP tools answer with, for the sections of the request's configuration, and takes its state from the request's writer, whether the agent registry holds a running agent for the review target, and whether the last start in the journal failed. `getReview` reads that activity only while the artifact is drafting. The page carries `progress` while drafting and `completion`, the text of the browser notification, once complete. The bands say which parts are unwritten (`isDraft` on a waypoint, a Journey Flow Diagram node, a trigger label, a File Section and the Context Section, `isTitleDraft` on a segment, `isUnassessed` on a Blast Diagram file, a `null` reading), and `progress.isWriting` says whether they are drawn as skeletons. The frontend derives none of it.
- **Instruction texts come from `packages/configurations`**, read once by `utils/instruction-file-reader/` from the `configurations` folder the build copies beside the server, and reached through `context.readInstructionTexts`. `procedures/get-instructions/utils/resolve-instructions.ts` resolves a field for a preset and falls back to Standard for what the preset does not write.
- **Agent conversations go through `conversationEnvironment`** (see [agent conversation](../../docs/vocabulary/agent-conversation.md)): the `ConversationStore` journal (`utils/conversation-file-store/` in the data directory), the `ConversationHub` that wakes every watcher of a review target (`utils/conversation-hub/` over `mqemitter`), the in-memory `AgentRegistry` of running agents and listeners, and one `AgentSpawner` per agent Flight Plan can start (`utils/claude-spawner/` runs interactive `claude` in a `node-pty` terminal). Every change to a conversation is appended and published with `appendAndPublish`, so the tRPC `conversation.watch` subscription and the agent's listening stream see it. `server/agent-lifecycle.ts` closes stalled and idle agents every 15 seconds and every agent on `onClose`.
- **Waiting is written without loops over `await`.** Turn a hub subscription into an async iterable with `readsOnChange` and consume it with `for await`, which `no-await-in-loop` allows.
- **Forge access goes through `packages/git-forge`**, imported as `@flightplan/git-forge`: one `GitAdapter` interface and the adapters for plain git, GitHub, GitLab, Bitbucket Cloud and Bitbucket Data Center. Its rules are in [packages/git-forge/AGENTS.md](../../packages/git-forge/AGENTS.md). What Flight Plan does with an adapter stays here: opening one for a repository (`utils/repository-adapter-opener/`), inspecting a repository (`utils/repository-inspector/`), finding a repository's forge, looking up authors, probing for a forge CLI and keeping credentials. An adapter that touches a subprocess takes its environment as an option, because only `main.ts` reads `process.env`.
- **`node-pty` is a native module** pinned to `1.2.0-beta.15`, the first release whose prebuilt `spawn-helper` keeps its execute bit and that ships Linux prebuilds. It stays external to the bundle, and `pnpm-workspace.yaml` allows its install script.
- **A package that is ESM-only cannot be required from the CJS build.** `@agntn/forges` and `@natoboram/bitbucket.ts` are bundled through `excludeFromExternal` in `project.json`. Do the same for a new package whose `exports` has no `require` or `default` condition, and run the built server (`node dist/apps/backend/main.js`) once, because tests (ESM) do not show the failure.
- **Fixtures exist in a development build only.** The build defines `IS_DEVELOPMENT_BUILD` (declared in `src/build-flags.d.ts`): `true` in the `development` configuration and in Vitest, `false` otherwise. Development-only code is reached through an `await import(...)` inside an `if (IS_DEVELOPMENT_BUILD)` and nowhere else, so esbuild leaves the module and everything only it imports out of a production bundle. Three such imports carry the fixtures: `procedures/list-repositories/index.ts` loads `procedures/list-fixtures/`, `procedures/get-review/index.ts` loads `procedures/get-fixture-review/`, and `main.ts` loads `utils/fixture-file-catalog/`, the only module that imports `@flightplan/playground-fixtures`, and puts it in the context as `fixtureCatalog`. The catalog reads `tools/playground-fixtures/test-cases` in place, at the path `main.ts` builds from the folder the server runs in, so a development build only runs inside the workspace and a rewritten snapshot shows without a rebuild. Nothing is copied beside the server: `.nxignore` hides the case repositories from the build's asset copy. A fixture case is a `Repository` like any other: `list-fixtures` picks the case `repository.list` was asked for in `fixtureCase` (the first one otherwise) and builds its line with `buildRepositoryLine`, and `repository.list` returns it with the test-case select as `fixtures`, which is `null` in a production build. A fixture row links to `/pr-reviews/<case>/<snapshot name>`, so `review.get` receives the case as its repository and the snapshot as its target: when no listed repository has that target, `getReview` asks `get-fixture-review` for a `ReviewSubject` (the repository, the target, the artifact the catalog reads as a `ReviewArtifact`, and a mocked target detail) and builds the page from it exactly as it does for a listed target. Do not add a route, a schema or a domain type for fixtures: give the fixture the production shape. A static import of these modules from code a production build reaches puts them in the bundle: after touching them, build for production and check that `main.js` does not contain `getFixtureRepository`.
- Validate every input with zod, and give every raw route a full schema including `response`.
- No request data in module-level state. Close every resource in `onClose`.
- Use `request.log` and `server.log`, never `console`.
- Load `fzf` with `await import("fzf")`, never a static import. The build leaves packages external and `require("fzf")` returns an empty module, which tests (ESM) do not show and only the built server does.
- File-system paths from requests or MCP calls must stay inside the repository root. Run subprocesses with argument arrays only.

## Layout

```
src/
  main.ts                                reads config, builds the server, listens
  server.ts                               buildServer: plugins, tRPC, MCP, raw routes, agent lifecycle
  config.ts                               pure environment parser
  procedures/
    context.ts                            ProcedureContext: the I/O procedures read through, and the mock context
    <procedure>/index.ts                  one procedure: the logic, transport-neutral, with __tests__/
    <procedure>/utils/                    schemas.ts and the pure modules only this procedure uses, with __tests__/
  <feature>/                              domain types, store interfaces and pure modules shared across procedures, with __tests__/
  server/
    trpc/trpc.ts                          createRouter and publicProcedure
    trpc/router.ts                        root appRouter, composed from routes/, and the AppRouter type the frontend imports
    trpc/plugin.ts                        mounts the appRouter at /api/trpc
    trpc/routes/<procedure>/index.ts      validates input, calls the procedure, maps its result to a TRPCError on failure
    mcp/plugin.ts                         the stateless MCP endpoint at POST /mcp
    mcp/tools/<tool>/index.ts             validates input, calls the procedure, shapes the MCP tool result
    api/plugin.ts                         registers @fastify/sse and the raw routes
    api/route-schema.ts                   turns a procedure's zod schema into the route's JSON schema
    api/routes/<endpoint>/index.ts        raw Fastify routes that tRPC cannot serve: the agent's listening stream and the spawned session's hooks
    agent-lifecycle.ts                    the idle-agent sweep and closing every agent on shutdown
  utils/<util>/                           I/O adapters, with __tests__/
```

## Verify

- `nx run-many -t eslint:lint typecheck test -p backend frontend` (the frontend type-checks against `AppRouter`)
- Test each procedure directly in `procedures/<procedure>/__tests__/index.spec.ts`, with a context holding in-memory fakes. Test each transport wrapper too, but only for what the wrapper does: validation and error mapping.
- Test Fastify and MCP with `server.inject(...)` on `buildServer()`, and never bind a port in tests.
- For a behaviour change, run `pnpm dev` and exercise the endpoint (tRPC through `/api/trpc/...`, MCP with a `tools/call` request) as well as the tests.
